## 1. 読む向きとページの左右

### 1.1 切り替えるのは表示位置だけ（決定 2026-09-29）
- 作品ごとに「右から」「左から」を持つ。企画の作品の設定で切り替える。
- 切り替えで動くのは、ページの表示位置だけ。絵・コマ割り・フキダシは反転しない。
- 反転しない理由：反転すると、利き手・絵の中の文字・着物の合わせが逆になる。

### 1.2 向きで変わるもの
| 変わるもの | 右から | 左から |
|---|---|---|
| 1ページ目 | 左に単独 | 右に単独 |
| 見開きの組（2-3、4-5…） | 変わらない | 変わらない |
| 見開きの前のページ（2-3なら2） | 右 | 左 |
| 構成・下のページ一覧の並び | 右から左へ | 左から右へ |
| めくりのページ（見開きの後ろ） | 左 | 右 |
| ノド側の影・ノンブルの位置 | ページが左右どちらに来るかに従う | 同じ |

### 1.3 見開き1枚の絵（私の判断）
- 見開き単位で1枚の絵として持つ。どちらの半分が何ページ目になるかは、書き出しのときに読む向きで決める。
- ページごとに半分ずつ持つと、向きを切り替えたときに絵がつながらなくなる。
- 絵は反転しないので、右から読む前提で描いた見開きを左から読む作品に移すと、フキダシを読む順が逆になる。検査で見つける（1.4）。

### 1.4 検査への影響（私の判断）
- 読む順・めくりの検査は、読む向きを入力に取る。
- 左から読むときは、コマを読む順も左上から始まる。コマ割りは反転しないので、右から読む前提のコマ割りのままだと、読む順の検査で落ちる。

### 1.5 海外版
- 海外版では、この切り替えを使わない。右から読むまま、セリフを訳文に差し替える（2章）。
- 英語版とフランス語版は、今は多くが右から読むまま出ている（調査 2026-10-09、`V3調査/4コマ・カラー・海外版の読む向きの調査.md`）。
  - 英語版は、2002年より前は大半が左右を反転していた。2002年に右から読むままへ移り、2018年の記事では反転が残るのは「ごく少数」。
  - フランス語版は、2011年の記事に「多くの出版社が元の向きを選んだ」とある。ベトナム語版は、大手の1社が全て右から読むままと述べている（2013年）。
  - 韓国語・中国語は出典が見つからなかった。ドイツ語・スペイン語は検索の要約だけ。数えた統計は見つからなかった。
  - 反転して出す版も少数ある。そのため、言語の版ごとに読む向きを選べるようにしておく（1.1 の切り替えを、言語の版でも持つ。私の判断 2026-10-09）。

## 2. 文字

### 2.1 文字の向きは読む向きと別に持つ（決定 2026-09-29）
- 縦書き・横書きは、読む向きとは別の設定。海外版は「右から読む・横書き」になるため。
- 持つ単位は言語ごと（私の判断。9章の2）。日本語は縦書き、英語は横書き、のように。

### 2.2 セリフと描き文字は絵と別に持つ（私の判断）
- セリフは絵に焼き込まず、文字として持つ。海外版は文字の差し替えだけで作れる。
- 描き文字（擬音）は、次の2つを両方持ち、1つずつ選べる。既定は「文字として置く」（私の判断。9章の3）。
  - 文字として置く：訳しやすい。手描きの勢いは出しにくい。
  - 絵の一部として描く：絵になじむ。訳すときは、残して横に訳を添えるか、消して描き直す。
- 画像生成が絵の中に文字を描いてしまったときに見つける手段は、未定。

### 2.3 言語ごとの版（私の判断）
- セリフの文字は言語ごとに持つ。フキダシの位置と話者は全言語で共通にする。
- 訳文がフキダシに収まらないときの手は、文字を小さくする・改行を増やす・フキダシを広げる、の3つ。どれにするかは言語ごとに人が選ぶ。収まらないことは検査で出す。
- 縦書きの約物（「！？」を横に並べる縦中横、長音の向き、小書きの位置）は自前で作る。描画に使うFabric.jsに縦書きが無いため（V3ハーネス設計 3.1）。

### 2.4 フォント（私の判断）
- セリフの種類（発話・心の声・叫び・ナレーション）ごとにフォントを割り当てる。
- 書き出しでフォントを画像にするときの使用許諾は、フォントごとに確認が要る（未確認）。

## 3. 媒体（決定 2026-09-29：3つとも同時に作る）

| 媒体 | 単位 | 構成の画面 | 検査で見るもの | 書き出し |
|---|---|---|---|---|
| 紙 | ページ・見開き | 見開きの並び（今の試作） | めくり・ノド・裁ち落とし | PSD・PDF |
| Webのページ型 | ページ | 見開きの並び | 見開きの使いどころ（電話の幅では見開きが1画面に収まらない） | ページごとの画像 |
| 縦読み | 1話の縦の帯 | 縦の帯に場面を並べる | コマの間の余白、1話の長さ | 決まった幅で分けた画像 |

- 試作での見せ方（2026-10-06）：企画の「媒体」を縦読みにすると、構成は場面を上から下へ並べた一覧（場面ごとの長さ付き）になり、原稿は1本の縦の帯になる。帯の左に場面の目次、帯の中に分け目の線、上の帯に全体の長さと分け目の数を出す。コマの間の余白は、場面の変わり目で広く取る。ツール（選ぶ・囲んで生成・コマ枠・ナイフ）は帯の上でもそのまま使える。Webのページ型は、紙と同じ画面を使う。書き出しで「分けた画像」を選ぶと、幅と分ける長さの欄が出る。幅800・長さ1280は例（調査した配信先の1つの値と同じ。配信先ごとの違いは下）。
- 縦読みには、ページ・見開き・めくりが無い。描き方の目安は次のとおり（調査 2026-10-09、`V3調査/縦読みの仕様と描き方の調査.md`。配信先の公式の手引き1つと、講座の記事から。手引き自身が「目安でありルールではない」と書いている）。
  - 画面に同時に入るコマは2つまで。フキダシは1コマに3つ以下。
  - コマの間は200px以上。場面や場所が変わるときは600〜1000pxの余白を取る。
  - 見せ場は、幅・形・大きさを変えたコマで作る。見せ場にするコマは、スマホの1画面にほぼ収める。
  - 文字は12〜30pxが多い。スマホの表示で確かめる。
  - これらは検査の閾値の初めの値に使う。「未検証」の印で持ち、設計7章の手順で確かめる。
- 縦読みの横幅と1枚の長さは、配信先ごとの規定として持ち、作品はそれを選ぶ（調査 2026-10-09）。
  - 横幅は、690・760・800・940 と配信先で違った。推奨が800の所が多い。
  - 1枚の縦の上限は、1280未満（超えると自動で分けられる）から20000までと違った。容量は1枚2MBの所が多い。
  - 公式の原文で確かめられたのは2つの配信先だけ。ほかは講座や個人の記事からで、古い数字が混じっている可能性がある。規定の値は人が直せるようにし、出どころと確かめた日を一緒に持つ。
  - 1話の長さの公式の目安は、見つからなかった。
- 紙と縦読みの両方に出す作品の組み替えは、手段が未定（V3ハーネス設計 18章）。
- 判型・仕上がり寸法・裁ち落とし・ノドの余白は、入稿先ごとの規定として持ち、作品はそれを選ぶ（調査 2026-10-09、`V3調査/入稿の規定の調査.md`）。
  - 裁ち落としは、調べた同人誌の印刷所3社とも3mm（うち2社は5mmも可）。
  - ノドの余白と、文字を入れてよい内側の範囲の数値は、どの入稿先にも書かれていなかった。値は空にして「未定」とし、人が入れる。
  - トンボは、不要と書いた所が2つあった。入稿先ごとに要・不要を持つ。
  - 4コマの原稿の寸法は、募集ごとに違った（横10×縦32cm、横8×縦22cm）。4コマも規定として持ち、作品が選ぶ。
- 色（白黒2階調・グレー・カラー）はページごとに上書きできる。扉だけカラーの作品のため。

## 4. 生成サービス

### 4.1 登録するもの
| 項目 | 内容 |
|---|---|
| 種類 | 画像・文章 |
| 接続先 | ローカルのComfyUIは送り先のURL。商用はAPIキー |
| 送り方 | 4.2 |
| 単価 | 1枚・1回あたり。人が入れる。提供元から自動で取れるかは未確認 |

- 画面は全作品で共通の「生成サービス」（上の右端の印から開く）。
- APIキーはサーバーだけが持つ（V3ハーネス設計 11章）。画面には末尾だけを出す（私の判断）。

### 4.2 送り方（決定 2026-09-29）
| 送り方 | 動き | 向く先 |
|---|---|---|
| 1件ずつ | 受けた順に1件送り、終わってから次を送る | ローカルのPCのComfyUI |
| 同時に N件まで | N件まで同時に送り、あふれた分は待たせる | 商用のAPI |

- サービスごとに切り替える。サーバーのキューは、サービスごとに分けて持つ。
- Nの既定値は2にする（私の判断 2026-10-09）。上限は決め打ちせず、接続先ごとに人が入れる。
  - 理由：提供元の同時実行の上限は、新規の契約で2件の所から、既定で24件の所まで幅があった。推奨を同時2〜4件とする所もあった。契約の段階で変わるので、アプリが決めると外れる（調査 2026-10-09、`V3調査/同時実行の上限と追加学習の費用の調査.md`。数字は確かめた日のもので、変わりやすい）。
  - 上限を超えたときの返り方が書かれていた提供元は、どこも「回数が多すぎる」を返すとしていた。待つ時間を返す所と返さない所がある。返されたらその時間だけ待ち、返されなければ4.5のルールで扱う。
  - ローカルのComfyUIは1件ずつ処理する（ComfyUIのソースで確認。試作でも、いくつ同時に送っても1件ずつ処理された）。
- 正本への書き込みは作品ごとに1本（V3ハーネス設計 9.3）。これとは別の話で、生成は並列でよい。
- 画面では、同時に走れる数を枠の数で、走っている数を塗った枠で見せる。

### 4.3 使い分け（決定 2026-09-29）
- 処理ごとに、送り先を1つ選ぶ（決定 2026-10-07。4.7）。それまでは、工程ごとに「作る」と「直す・作り直す」の2つを選ぶ形だった。
- 既定（私の判断。9章の7）：作る処理は費用の安い先、直す処理（絵から作り直す・囲んで直す）は得意さの高い先。
- 1回ごとに選び直せる。原稿の「生成」の横の設定で選び、ボタンに送り先と費用を出す。
- 作品の「送ってよい先」（V3ハーネス設計 4.2）に無いサービスは選べない（私の判断）。
- 候補には、どのサービスで作ったかを出す。

### 4.4 キューの順番（私の判断）
- 人が画面で依頼したものを先にする。AIが工程を進めるための生成は後。人が画面の前で待っているため。
- 同じ扱いの中は、依頼した順。
- 人は、待ちの順番を入れ替え、取り消せる。
- 作品をまたぐ順番は未定（V3ハーネス設計 2.4の29）。

### 4.5 失敗したとき
別のサービスへ自動で回さない（決定：方針7）。種類ごとの扱いは次のとおり（私の判断）。

| 失敗 | 扱い |
|---|---|
| 回数・同時実行の制限 | 待つ状態にし、同じサービスに送り直す（方針8） |
| 時間切れ・通信の失敗 | 同じサービスに送り直す。回数を超えたら止めて人に通知する |
| 内容で断られた | 記録して止め、人に通知する。送り直さない |
| 返ってきた形が崩れている | 失敗として記録し、使わない |
| 予算の上限 | 待つ状態にする（方針8）。人が上限を上げるか、月が変わるまで待つ |

- 止まったものはキューに残す。人が「もう一度」か「サービスを選んで送る」を押す。
- 工程を止めているなら、判断待ちにも入れる。
- 送り直しの回数（通信の失敗）と、作り直しの回数（出来が悪い）は別の設定にする。

### 4.6 費用
- 生成する前に、ボタンに費用を出す（単価×枚数）。文章は長さで変わるので、見込みの額になる。
- 予算は、全体の月の上限と、作品ごとの上限の両方を持つ（私の判断。9章の6）。上限の何%で止めるかを選ぶ。
- ローカルのComfyUIは費用0として数える。
- 待ちを取り消したときは費用はかからない。生成中に止めたときに課金されるかは、提供元による（未確認）。

### 4.7 接続先と、処理ごとの送り先（2026-10-07）
- 今のアプリの設定の窓を確かめた（`js/ai/role/ai-roles.js`、`js/ai/role/role-assignment-ui.js`、`index.html` の設定の窓）。
  - 処理10種類（文から絵、絵から絵、囲んで直す、拡大、背景を抜く、角度、絵から指示を読む2種、指示を書く、絵を文章モデルで読む）と、接続先7つの表。処理ごとに送り先を1つ選ぶ。できない組み合わせは選べない。
  - 接続先ごとに、処理ごとのモデル、同時に送る数、APIキーかURLを持つ。ComfyUIはワークフローを種類ごとに持つ。
  - 得意不得意と費用は持っていない。
- V3も同じ形（処理と接続先の表）にし、セルに得意さと1回の費用を足す（決定：利用者の指示 2026-10-07。処理ごとに得意不得意がある、費用でこちらが良いという場合もある、これはこっち・これはあっちを決める設定画面が要る）。
- 表：行は処理（工程ごとにまとめる）、列は接続先。画像と文章で表を分ける。セルには得意さ（◎得意・○ふつう・△苦手）と1回の費用を出す。セルを押すと、その処理をその先へ送る。取り消せる。できない組み合わせは押せない。
- 処理（試作の16個。私の判断）：
  - 画像：ラフを作る、人物の絵を作る、絵を作る、絵から作り直す、囲んで直す、角度を変える、顔・手を直す、白黒化・トーン、拡大、背景を抜く。
  - 文章：構成・コマ割り、セリフ、翻訳、指示を書く、絵から指示を読む、検査・評価。
- 得意さは人が付ける（私の判断）。提供元の説明や推測では決めない。判断の材料として、接続先ごとの実績（採用した数と送った数、採用1つあたりの費用、平均の時間）を並べる。実績は採用・却下の記録から数える（数え方は未設計）。
- 「同じ指示で比べる」：同じ指示を、送れる先すべてへ送って見比べる。費用がかかる。試作では見た目だけ。
- 費用は、接続先と処理の組ごとに持つ。同じ先でも処理で違うため。人が入れる（4.1）。
- 中身（12章）も、接続先と処理の組ごとに持つ。ComfyUIはワークフローとモデル、APIはモデルの名前。送り直しと作り直しの回数（4.5）は処理ごとに持つ。
- 生成サービスの画面には右のパネルを置かない（決定 2026-10-07。右のパネルが押した場所で別物に替わり、同じ操作が中心と右の両方にあって、利用者から「直観的じゃなくてよくわからん」と言われたため）。画面は「処理ごとの送り先」と「接続先」の2つのタブに分ける。
- 「処理ごとの送り先」のタブ：セルを押すと送り先が決まる。行の名前を押すと、その行の下に細かい設定が開く。開いた中は、接続先の列にそろえて、得意さ・1回の費用・採用した数・採用1つあたりの費用・平均の時間・ワークフロー・モデルを並べる。その下に、送り直しと作り直しの回数、「同じ指示で比べる」を置く。
- 「接続先」のタブ：接続先1つを1枚のカードにする。状態、一時停止、URLかAPIキー、接続を試す、送り方、いまの実行状況、入っているもの、止まったもの、商用利用の条件（押すと開く）。表の列の見出しを押すと、このタブのそのカードへ移る。
- 接続先：ローカル（ComfyUI、ローカルの文章モデル）とAPIを、同じ形で並べる。違いは、接続先がURLかAPIキーか、費用が0かどうかだけ。
- 接続先ごとに状態を持つ：接続済み・止まっている・APIキーが無効・未確認・一時停止中。列の見出しの印で見せる。
- 一時停止：人が手で止める。ローカルのPCを別の用途に使うときのため。一時停止した先へ依頼したものは待ちに入り、再開すると順に送る。
- プリセット：送り先の全体を1回で切り替える。安く・得意を優先・ローカルだけ・APIだけ。送れる先だけから選ぶ。選べる先が無い処理は変えずに、そのことを通知する。切り替えるのは人で、自動では切り替えない（方針7）。
- 送れない先を使っている処理があるときは、上の帯のキューの印と、生成ボタンと、表のセルに出す。依頼したものは待ちに入る（4.5）。
- ローカルのComfyUIは、入っているモデル・追加学習・ワークフローの数を再読み込みできる。ワークフローに要るモデルが無いときは印を出す。
  - ComfyUIから一覧を取る API は、ComfyUI 0.38.0 で動いた（2026-10-09。GPUを使わない起動で確かめた）。取れたのは、モデルの種類の一覧、種類ごとのファイルの一覧（絵のモデル2つ・追加学習92個）、ノードの一覧（3,116個）と各ノードで選べる値。
  - ワークフローに書かれたモデルの名前を、この一覧と比べれば、無いモデルが分かる。比べる処理そのものは作っていない。
- 止まったもの（4.5）は、接続先のカードに出す。「もう一度」と「先を選ぶ」。
- 試作で動くもの：セルを押して送り先を変える・取り消す、得意さを付け直す、プリセットの切り替え、接続を試す、一時停止。見た目だけのもの：接続先を足す、再読み込み、同じ指示で比べる、もう一度、いまの並びをプリセットに保存、費用と中身の欄。
- 試作の接続先の名前は、今のアプリにある接続先の名前を借りた（文章の1つはV3の試作で使っているもの）。得意さ・費用・実績の数字はすべて例で、調べた値ではない。
- 未決：作品ごと・人物ごとに送り先を変えられるようにするか（12章の「決まる順番」との関係）。

## 5. 判断待ち

### 5.1 番号と印（試作で採用）
- 番号は全画面で1本。前後の送りも、全画面を通して回る。
- 印の形：判断待ちは橙の丸、検査の失敗は赤の角丸、人の書き込みは書いた人の頭文字。
- 赤は検査の失敗だけに使う。赤入れの線そのものは赤のまま。

### 5.2 並び（私の判断）
- 工程の前のものから（構成→設定資料→ネーム→作画→仕上げ）。
- 同じ工程の中は、後ろの工程を止めている数が多いものから。

### 5.3 採用・却下・取り消し
- 採用のボタンの上に、捨てるもの（描き直しになるページ）と、残っている失敗を出す（試作で採用）。
- 却下は止まるだけ。作り直しは、人が「生成」で指示する（私の判断）。自動で作り直す設定も持つ（9章の4）。
- 理由：理由を付けずに作り直させると、前と同じ物が出るのではなく、前から大きく離れる。直してほしい所と関係なく変わる（2026-10-08 に根拠を改めた）。
  - 試作 p30（一覧 6-4、`V3検証の結果.md`「6-4 理由なしの作り直し」）：LLM に作画用の言葉を作らせ、却下だけを伝えて作り直させた。前の言葉との重なりは、理由なし 0.374・理由あり 0.46。理由なしの作り直しどうしは 0.524 で似た。
  - もとの根拠「理由が分からないまま作り直すと、同じ物が出やすい（推測）」は、この結果と逆だったので外した。
  - 理由ありの作り直しが、指摘した所を直せたかは測っていない。絵での比較も未検証。
- 採用・却下は取り消せる。取り消したとき、その後に進んだ後ろの工程は消さず、「古い」印を付ける（私の判断）。

### 5.4 上流を変えたときに古くなるもの（私の判断）
| 変えたもの | 古くなるもの |
|---|---|
| 企画 | 構成すべて |
| 構成（ページの割り当て） | 割り当てが変わったページのネーム以降 |
| 設定資料（キャラのルール） | そのキャラが出るコマの検査結果 |
| ネーム | 変わったコマの作画以降 |
| 作画 | そのコマの仕上げ |

- 古くなったものを自動で作り直すかは、企画の「AIを止める所」に従う。既定では自動で走らせない（自動で走る機能は設定で切れるようにする、という以前からのルール）。
- 手動で修正した所（確定印、V3ハーネス設計 9.2）は、古くなっても自動で上書きしない。
- 設定資料を変えたときは、絵を作り直さず、検査だけをやり直す。

## 7. 書き出し
- 書き出すページは人が選ぶ。ネーム済より後のページなら選べる（試作で採用）。ネームを編集者に出す用途のため。
- 失敗が残っていても書き出せる。ボタンの上に、残っている数を出す（試作で採用）。
- 形式はPSD（レイヤーを分ける）・PNG・PDF。縦読みは分けた画像（3章）。
- ページの左右とノンブルの位置は、読む向きで決まる（1.2）。
- ファイル名は「作品の略号_話_ページ3桁」（試作の例 kiri_03_001）。
- 解像度の既定は、入稿先の規定から取る（調査 2026-10-09、`V3調査/入稿の規定の調査.md`）。
  - 白黒2値は600dpi。調べた同人誌の印刷所3社と、商業誌の応募規定3誌がすべて600dpi（商業誌は600以上）。トーンは600の倍数で、1200も可とする所が1社。
  - カラーは350dpi。グレー（トーンなし）は300〜350とする所と、600とする所があった。
  - 電子書籍は、dpiではなくピクセル数で決まる（1つの配信先は300ppi以上・JPEG）。
  - 取得した文は小型モデルの要約を通っていて、原文との照合はしていない。

## 8. 画面のルール
- 明るい表示だけにする。暗い表示は持たず、切り替えも作らない（決定 2026-10-08）。
  - 色は砂とベージュのカラーテーマにする。NieR:Automata のような、砂漠の明るい色合いで、淡い砂色の地に、濃い茶色がかった灰色の文字と線を置く。強い色は、選んでいる物と警告の印だけに使う。
  - 原稿のページ・候補の絵・設定資料の絵・ツールの見本は紙なので、地の色を乗せず白いまま見せる。
  - 経緯：2026-10-06 に「灰色の暗い表示」に改めたが、利用者の以前からの好み（暗い表示は使わない、明るい表示だけ）を優先して戻した（2026-10-08）。2026-09-28 の「明るい表示だけ」と同じ向き。
- ダッシュボード風の表示と、初心者向けの説明付きの部品を使わない。状態はページの上の印と絵の段階で見せる（決定 2026-09-28）。
- 生成はすべてキューを通す。自動で走る機能は設定で切れるようにする（以前からのルール 2026-08-29）。
- 電話の幅では、ページを縦に並べ、判断のボタンを画面の下に固定する（試作で採用）。
- 画面上のツールは、上の中央の1本の帯にまとめる（試作で採用）。
- 原稿の右のパネルは「判断・ツール・レイヤー」の3つを切り替える（試作で採用 2026-10-06）。ツールを選ぶと右のパネルはそのツールの設定に替わる。コマやフキダシを選ぶと、その物の設定に替わる。判断の印を押すと判断に戻る。
- 上の帯の右に、キュー・探す・通知・キーの一覧・生成サービス・設定・人を置く。作品名と話の名前を押すと、作品と話の切り替えが開く（試作で採用 2026-10-06）。
- 今のアプリにある機能は、置き場所を変えて原稿のツールと各画面へ入れる（決定 2026-10-06）。対応は10.4。統計の一覧だけは入れない（上のルール）。
- 削除したページは消さずに取っておく。構成の上の帯の「削除したページ」から戻せる。原稿では、何も選んでいないときの右のパネル「並び」で削除・戻す（試作で採用 2026-10-06）。
- どの操作にもキーを割り当てる（22章）。

### 8.1 カラーテーマ（決定 2026-10-08）
- 色は、あとでカラーテーマごと替えられるようにする。今あるカラーテーマは「砂漠」だけで、カラーテーマを選ぶ画面と、ほかのカラーテーマは作らない（利用者の指示）。
- ルールは `v3/web/common/theme.css`。値は持たず、色の名前と意味だけを書く。値は `v3/web/common/themes/desert.css` が持つ。使うカラーテーマは `theme.css` の末尾の `@import` の1行で決める（ここ1か所）。
- 画面の CSS と JS は名前（`var(--名前)`）だけを使い、色の値を書かない。原稿・工程の画面も同じ。
- canvas に描く色（囲んだ範囲・手動編集の範囲・ペンの先）は、`v3/web/common/theme_colors.js` の1か所で `getComputedStyle` から読む。名前が無ければ止める（代わりの色で描かない）。工程の図（Cytoscape）は `harness/harness_graph.js` が同じやり方で読む（Cytoscape は CSS の変数も `color-mix()` も読めないので、要素の色に当ててブラウザに解かせる）。
- 試験：`node v3/web/test/theme_check.mjs`（ブラウザは要らない）。カラーテーマのファイルの外に色の値（`#…`・数の入った `rgb()` など・`white` などの名前）が無いことと、どのカラーテーマにもルールの名前が全部あることを確かめる。今は名前 52 個、色の値 0 件。
  - 決め打ちを許すのは、行に `色の決め打ちを許す：理由` と書いた所だけ。今は、画像生成のペンの墨（`#000000`。描いた線は絵のデータになる）・囲んだ範囲を書き出すときの白（マスクの値）・企画の色の欄に入力の形の例として薄く見せる文字（`#000000`）。
  - ファイルごと許すのは `manuscript/js/print_colors.js` だけ。理由：原稿のデータとして刷る黒と紙の白で、書き出しにそのまま入る。画面のカラーテーマを替えても変えてはいけない。
- カラーテーマを足すとき：`themes/<名前>.css` を作り、ルールの名前を全部書く（紙の物 `.paper,.cand` の中で替える名前も）→ `theme.css` の `@import` の1行を替える → `theme_check.mjs` を流す。
- 名前（意味は `theme.css` に書いた。ここは一覧）：

| 種類 | 名前 |

| 地 | `--bg` `--canvas` `--dot` `--surface` `--surface-2` `--surface-3` `--on` `--raise` `--glass` |

## 10. 人が直接描く・直す（私の判断）

### 10.1 ツール（試作で採用）
- 原稿の上の帯に、AIに頼むツール（選ぶ・囲んで頼む・赤入れ）と、人が描くツール（ペン・消しゴム・文字・コマ枠・ナイフ・フキダシ・トーン・図形・手のひら）を並べる。その右に、読む順・表示するもの・取り消す・やり直す・拡大縮小を置く（2026-10-06 に追加）。
- ナイフ：コマを押した所で2つに分ける。向きは横・縦・斜めを選ぶ。斜めは角度を決める。切る線は、押す点を通る1本の線として、押す前から見える。分けた間の幅は「コマの間」で決める。絵は大きい側に残り、分けた2つのコマに手描きの印が付く（10.2）。細すぎる分け方は受け付けない。斜めに切ったコマは四角でない形になり、もう一度切ることも合わせることもできる。
- トーン：網点・線・砂目・グラデ・雪・集中線・スピード線。線数・濃さ・角度と、貼る所（コマ・囲む・塗る）を選ぶ。
- 図形：絵記号を探して置く。線・塗り・影を決める。
- 手のひら：原稿を掴んで動かす。
- コマ枠：枠の線を掴んで動かす。線を引いて1つのコマを分ける。隣の2つを合わせる。合わせるときは、コマ枠のツールで「合わせる」を選び、2つを順に押す。2つを包む1つの形になり、中身は大きい側のものが残る。隣り合っていない2つは受け付けない。
- フキダシ：動かす・大きさを変える・しっぽの向きを変える・形を変える。セリフは、フキダシを2回押して、その場で打つ。
- 文字：写植と描き文字を置く（2.2）。
- ペン・消しゴム：手描きのレイヤーに描く。消しゴムはAIの絵のレイヤーにも効く。消した跡は手描きとして扱う（10.2）。

### 10.2 手動で修正したところを守る
- 人が描いた・動かした・消したところに「手描き」の印を付ける。
- AIに作り直させるとき、手描きの範囲は描き直す範囲から外す。
- 手描きの印を外せるのは人だけ。
- 理由：AIが人の直しを上書きすると、同じ直しを2回することになる。
- 守り方は、描き直した後に、手描きの範囲を元のピクセルで貼り戻す（試作 p05、`V3検証の結果.md` の 1-24）。
  - 描き直す範囲の指定だけでは、人の範囲の78％のピクセルが変わった（目に見える差は11％）。
  - 指定に加えて元のピクセルを貼り戻すと、変化は0％だった。貼り戻しはComfyUIの標準の部品でできた。
  - 試したのは絵1枚・描き方1種。画像編集のサービス（外のAPI）で同じ守り方ができるかは未検証。

### 10.3 1ページのレイヤー
- 下から、紙（白）、コマごとの絵（グループ。コマの地・コマの絵・レイヤー）、トーン・図形、コマ枠、人の手、フキダシ、写植、描き文字の順に重ねる（2026-10-08 に変更）。
- コマ枠をコマの絵より上に置く。理由：試作 p59 で、枠を絵の下に置いた PSD は、絵の不透明な所が枠を隠し、枠の線の 49.8% が見えなかった。
- 紙のレイヤーを一番下に置く。理由：紙が無いと、PSD を開いたツールによって、透明な所の見え方（白か市松か）が変わる。
- どのレイヤーの名前も「名前 [id]」で終わる。id は正本の行の id か、ページ・コマの id に「-paper」などを付けたもの。PSD を戻すとき、この印でレイヤーと行を結び付ける（Krita が名前の後ろに足す NUL と、GIMP が足す「 #1」は外して読む）。
- ペンの線は、線のデータ（点の並び・筆・太さ・色）が正本。手描きレイヤーの絵は線から作った画像で、画面（ブラウザ）が描いてサーバーへ上げる。理由：今のアプリの筆（fabric.js）を画面が持っているので、見えている絵と線の画像が同じになる。線の画像には、どの線のバージョンから作ったかを残し、古い線の画像はAIへ渡す絵にも書き出しにも使わない。
- PSDの書き出しでは、このレイヤーごとに分ける（7章）。ペンの線はPSDではピクセルのレイヤーになる（線のデータはアプリに残る。PSD から線には戻らない）。書き出しの画面にもそう書く。
- 手動で修正したPSDを戻すとき、ピクセルの変わったコマの絵・レイヤーは新しいバージョン（手動で修正した絵）にする。線や形から描いたレイヤー（コマ枠・フキダシ・トーン・図形・線の画像）と文字のレイヤーのピクセルが変わったとき、どの物にも当たらないレイヤー、無くなったレイヤーは、判断待ちにして人が選ぶ（文字は、打ち直す・絵として採る・捨てる）。

### 12.1 人物の特徴と表情の強さ（私の判断 2026-10-09）

## 13. 書き出しの大きさ（私の判断）
- 生成するときの大きさと、書き出すときの大きさは分けて持つ。
- 書き出しの大きさの例：B5判（182×257mm）を600dpiで出すと、約4300×6070ピクセルになる（計算）。
- 生成は小さめに作り、書き出しの前に拡大する。拡大はキューを通す仕事にする（8章）。
- 書き出しの画面で、拡大が済んでいないページに印を出す。
- 拡大で線が崩れていないかは、人が見る。
- 拡大は、線は保てたが、網点のトーンが壊れた（試作 p04、`V3検証の結果.md` の 1-26。832×1216 の1枚を B5・600dpi へ拡大）。
  - 単純な拡大は、トーンが残り、線がぼやけた（3.7秒）。
  - 拡大用のモデル3種は、線はくっきりしたが、トーンが消えて平らな灰色になるか、別の模様に変わった（4.8〜9.1秒）。うち1種（4x-UltraSharp）は非商用。
  - くっきり度の数値は、トーンを消した方式ほど高く出た。数値で方式を選ばない。
  - そのため、トーンは拡大と分けて持つ。拡大の前にトーンを分けておくか、拡大の後に貼り直す。どちらの手が使えるかは未検証（レイヤーを分ける試作 p20 では、分けたトーンは網点ではなく灰色になった）。
- 白黒の印刷では600dpiが要る（7章。調べた印刷所3社と商業誌3誌がすべて600dpi）。B5の裁ち落とし込み（188×263mm）は、600dpiで4441×6213ピクセル（印刷所のテンプレートの値）。カラーは350dpi、電子書籍はピクセル数で決まる。

## 22. ショートカットキー・全画面・集中モード（試作で採用。共通の部品にした 2026-10-08）

### 22.1 ルール
- キーを押すのは、画面のボタンを押すのと同じにする。キーのための処理を別に作らない（1か所で押す）。
- ボタンに指を置くと、そのボタンのキーが出る。ボタンの `<kbd>` と `title` は、割り当てから書く（`data-key="操作の名前"` を付けたボタン。キーを変えるとすぐ書き直す）。
- 描くツールのキーは、Photoshopと同じ割り当てにする（V・B・E・T）。
- 割り当ては、利用者ごとに変えられる（22.4）。

### 22.2 キーの割り当ての作り（共通の部品）
- 全部の画面の割り当ては1つの一覧 `v3/web/common/key_catalog.js` に書く。1件は「操作の名前・どこで効くか・名前・キー」。画面のコードは、操作の名前に処理を結ぶだけ（`km.bind("workbench.pen", …)`）。キーを受けるのは `v3/web/common/keymap.js` の1か所。
- どこで効くか（scope）は3段：ツール（`画面:ツール`。例 `workbench:mask`）→ 画面 → どの画面でも（`global`）。同じキーなら狭い方が先に効く。
- 同じキーを、わざと重ねてよい物がある（`chain`）。Esc・Tab・矢印。狭い方の処理が「することが無い」と返すと、次の物へ回す。Esc はこれで「ツールの途中をやめる → 画面の物を閉じる → 集中モードから抜ける → 全画面から抜ける」の順に1つずつ抜ける。
- 押している間だけ効く物（`hold`）：Space（手のひら）。離すと元のツールに戻る。ブラウザの窓から外れたときも離したことにする。
- 続けて押すキー：「G のあと 1」のように、1秒の間に2つ押す。
- Ctrl と ⌘：割り当ては `$mod` と書き、Mac では ⌘、ほかでは Ctrl にする（`navigator.platform` で見分ける）。Mac の Option は文字を変える（⌥+L が ¬ になる）ので、キーを変えるとき Option と組んだキーは位置（`e.code`）で保存する。
- 文字を打っている間（入力の欄・文の欄・`contenteditable`）は、画面のキーは効かない。そこで効くのは、印を付けた物だけ：Esc（欄から出る）と Ctrl+Enter（生成）。
- IME の変換中は、どのキーも効かない。`KeyboardEvent.isComposing` か `keyCode` が 229 の物を捨てる（MDN の KeyboardEvent.isComposing の説明と同じ扱い。https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing ）。
- 開いている窓（`dialog`）の中のキーは、その窓が受ける。閉じた窓の入力の欄に入ったままのキーは、欄から出して画面のキーとして受ける（Chromium で、Esc で閉じた直後に入ったままのことがあり、キーが全部止まっていた。試験で見つけて直した）。
- キーを受ける部品は tinykeys 3.0.0 を `v3/web/vendor/tinykeys-3.0.0/` に置いて使う（MIT。https://github.com/jamiebuilds/tinykeys ）。選んだ理由：`$mod` で Ctrl と ⌘ を替える書き方と、続けて押すキーの書き方を持ち、650バイトほどで小さい。キーの書き方を読む所（`parseKeybinding`）と、押したキーが合うかを見る所（`matchKeyBindingPress`）だけを使い、どれを先に効かせるか・重ねる・押している間は自分で書いた（tinykeys の API は合う物を全部呼ぶので、狭い方を先にできない）。tinykeys は修飾キーを厳しく見るので、`?` と `+` は `Shift+?`・`Shift++` と書く（`+` は Shift 無し（テンキー）と有りの2つを持つ。見せるときは1つにまとめる）。

### 22.3 キーの一覧
- `?`（Shift+?）か、画面の帯の「キー」で出す。今の画面と今のツールで効く物を、効く順（ツール → 画面 → どの画面でも）に並べる。結んである物だけを出す。
- 上の欄で、名前とキーの両方から探せる。
- 印：押している間・この画面にまだ無い（キーは空けてあるが機能が無い）・変えた。
- 窓の下に、Mac のキーと IME のルールを書く。電話の幅では、帯の「キー」の文字を隠し、印だけ出す。

### 22.4 キーを変える（利用者ごと）
- 画面の帯の「キー」→「キーを変える」か、キーの一覧の「キーを変える」から開く。全部の画面の割り当てを出し、今の画面を先に並べる。
- 1件ごとに「足す」（押したキーを録る。Esc でやめる。押している間の物は Alt などの修飾キーだけも録れる）・キーを外す・「初めに戻す」。
- 重なり：足そうとしたキーが、同じ所で効く別の物と重なると、窓の中に赤い通知を出して、まだ保存しない。「相手から外して割り当てる」か「やめる」を選ぶ。重なりの判定：効く所が同じか、どちらかが「どの画面でも」か、片方がもう片方のツールの段か、で、文字を打っている間かどうかも重なり、どちらも `chain` ではなく、キーが同じか、続けて押すキーの頭が同じ。一覧の上には、今の割り当て全部の重なりを出す（初めの割り当ては 0 件。試験で確かめる）。
- 全部を初めに戻す（確かめてから）。
- 今のアプリのキーを読み込む：今のアプリで違うキー（F1・Ctrl+8・Ctrl+9・Ctrl+0・Alt+←→ など）を並べ、読み込むと足す（V3 の初めの割り当ては消さない）。V3 に無い物（Ctrl+G など）は理由と一緒に並べるだけ。
- 保存する所：サーバーの利用者ごとの設定 `GET/PUT /me/settings` の `other.keymap`（`{操作の名前: [キー]}`。初めと違う物だけ）。PUT は全部を書き換える API なので、読んでから `language`・`autosave`・`autosave_interval_seconds` と `other` のほかの値をそのまま付けて送る。ほかの端末でも同じ割り当てになる。localStorage には保存しない。
- 読めないとき・利用者の名前が無いときは、初めの割り当てで動き、キーの一覧とキーを変える窓に「…初めの割り当てで動いています」と出す（黙って代わりの物を使わない）。

### 22.5 全画面と集中モード
- 2つを分ける：
  - 集中モード（Shift+F）：ページの中で、パネルを隠して絵の所を広げる。ブラウザの帯は残る。
  - 全画面（Ctrl+Shift+F・⌘+Shift+F）：ブラウザの Fullscreen API（`requestFullscreen`）で画面いっぱいにする。
- 画面ごとの集中モード：
  - 原稿：絵（ページ）だけ。ツールの帯は残す。
  - 画像生成：絵と、下に候補の帯（候補だけを横に並べる）。ツールの帯は残す。
  - 工程：図だけ（見張る画面として使う）。図の色の説明と「全体を見る」は残す。パネルが出入りしたら図の大きさを合わせ直す。
  - 確認：「読み通す」。ページを大きく1枚ずつ出し、矢印は作品の読む向きに合わせる（右から左の作品では ← が次）。PageDown・PageUp は向きによらず次・前。ページの絵を返す API がまだ無いので、番号・状態・コメントを出す。
  - 作品をまたぐほかの画面（作品と話・企画・構成・設定資料・書き出し・生成サービス・取り込み・翻訳）：上の帯と画面の帯を隠す。
- Tab：集中モードのとき、パネルを一時的に出す・隠す。集中モードでないときは、Tab は普通の移動のまま。
- 右下に小さい帯（パネル・全画面・抜ける）を出す。キーを知らない人もマウスで戻れる。
- Esc の順：ツールの途中 → 集中モード → 全画面。全画面のとき Chromium では Keyboard Lock（`navigator.keyboard.lock(["Escape"])`）で Esc をページが受ける。このとき Esc を長く（2秒）押すとブラウザが全画面を抜ける（WICG の Keyboard Lock のルール。https://wicg.github.io/keyboard-lock/ ）。Keyboard Lock の無いブラウザでは、1回目の Esc でブラウザが全画面を抜ける（未検証。Chromium 以外では確かめていない）。
- ブラウザの側で全画面を抜けたとき（Esc・F11・ブラウザのボタン）は `fullscreenchange` を受けて、画面の印を合わせる。集中モードはそのまま残る（試験で確かめた）。
- 覚える：集中モードかどうかは画面ごとに、このブラウザの localStorage `v3.view.<画面>` に保存する（見た目の好みなので、サーバーには保存しない）。全画面は開き直したときに戻さない（ブラウザが、人の操作なしの全画面を許さない）。
- 状態は `<html>` の `data-focus`・`data-peek`・`data-fullscreen` で見せ、隠すパネルには `data-v3-panel` を付ける（CSS の1か所 `common/keys.css` で隠す）。変わると `window` に `v3-view` の出来事を送る。

### 22.6 ポインタ
- 修飾キー（Ctrl・⌘）+ホイール：広げる・縮める。ホイールだけ：上下に動かす。Shift+ホイール：左右に動かす。原稿の画面と同じにした（画像生成の画面は、ホイールだけで広げていたのを改めた 2026-10-08）。
- Space+ドラッグ：手のひら（押している間）。
- タッチの2本の指で広げる：トラックパッドの2本の指はブラウザが Ctrl+ホイールとして送るので、上と同じに効くはず（未検証。実機で確かめていない）。タッチの画面の2本の指は、まだ作っていない。
- ペンの横のボタン：まだ作っていない（未検証。ブラウザの `pointerdown` の `button` で見分けられるかを確かめる）。

### 23.1 見せる場所は3つ
1. **原稿のページの上**：AIが扱っているコマの右下に印を出す。
   - 印の中身：いまの段階（絵を作っている・比べている・確定）、候補1枚ごとの点（検査を通った・落ちた・作っている・まだ）、作り直しの回。
   - 絵を作っているコマだけ、コマの上に光を流す。待ちのコマには流さない。
   - 確定したコマは黒い線で、まだのコマはネームの線のまま描く。ページ全体を1つの状態にしない。
2. **右のパネルの「経過」タブ**：選んだコマについて、次を上から順に並べる。
   - 指示：設定資料から組んだ固定の部分（鍵の印）と、コマごとに書いた部分（距離・角度・向き・動作・表情）。書いた接続先の名前。
   - 回ごとの候補：絵と、検査で落ちた理由。作っている途中と待ちの候補も同じ並びに置く。
   - 作り直しの前に、指示のどこを直したか。同じ失敗が2回続いて指示を一から書き直したとき（設計10章の6）は、その印。
   - 2枚ずつ比べた結果：左右を入れ替えた2回の判定、観点、勝ちか引き分けか（設計8.1の4）。
   - 上限の回数に達して止まったときは、判断待ちへの行き先（設計10章の8）。
   - 呼び出しの記録：時刻、処理、接続先、時間、費用。行を開くと、送った文と返ってきた文（設計10章の9、13章）。
   - 下の欄：指示を足して生成、止める、作り直す。動いている途中で生成すると、いまの回を止めて始め直す（設計13章「指示の変更」）。
3. **キュー（画面の右上）**：接続先ごとに並べる。
   - 同時に送れる数と、いま使っている数。
   - 動いている処理：処理の名前、済んだ数、作り直しの回、経過時間、費用。コマの行を押すと、そのコマの経過が開く。
   - 待ちと、その順番。
   - 失敗して止まったもの：理由と回数、「もう一度送る」「送り先を選ぶ」（4.5）。

### 23.2 決めたこと
- LLMの途中の考えの文を、画面に常に出さない。常に出すのは判断の結果（落ちた理由・比べた結果・直した所）にする。送った文と返ってきた文は、呼び出しの記録から開いたときだけ出す。理由：ページそのものを作業の中心にし、説明の文で画面を埋めないため（8章）。
- 右上の数は「実行中」と「待ち」にする。「生成中」は絵を作る処理だけを指す言葉なので、比べる・指示を書くを含む数には使わない。
- 経過は、コマを単位にする。作画はコマごとに候補を作って選ぶため（設計8.1）。

- 迷っていた言葉は、次のとおりに決めて直した（私の判断。利用者の「やれるところは全部」2026-10-09）。頼む → 生成（生成を始める操作。囲んで頼む → 囲んで生成）と依頼（人や順番待ちに出す物。直しを頼む → 修正を依頼、頼んだ → 依頼済み）、絵だけ → 集中モード、保存の具合 → 保存の状態、進み具合 → 進行状況、決めごと（画面の見出し）→ 作品の設定、抜く → 削除（抜いたページ → 削除したページ）、抜き出す → 抽出、人が書いた項目 → 手動で入力した項目、人が直した → 手動で修正、人が描いた → 手描き、人が確定 → 手動で確定、評価役 → 評価モデル、版 → バージョン（昔の版 → 前のバージョン）、吹き出し → フキダシ、つながる → 接続（サーバーにつながりません → サーバーに接続できません）、招いてもらう → 招待してもらう、段 → ステップ（工程の画面。段の切れ目で止める → ステップの区切りで止める）。画面の通知に出ていたこの文書の章の番号は消した。
- そのまま残した言葉と理由：「人の判断」（工程のステップの名前。英語は Review と Needs decision に分けた）、「描き足す」（絵の外側を広げる処理の名前として通じる）、「順番待ち」（状態の名前。物の名前は「キュー」。英語は Queued と Queue）、翻訳の画面と設定資料の画面の「残す」（消さずに置いておく意味のボタン。保存の意味ではない）。
- 文書とコードのコメントも同じ表で直した（2026-10-09。`llm_doc/` の14ファイルと `v3/web/` のコメント）。文書ごとに言い方が分かれて残っているもの（置き場・操作の窓口・呼び出し口・名乗り方・下ごしらえ など）は、一般の言葉に替える候補だが、数が多いので直していない。

### 24.2 多言語
- 画面の文言は、言語ごとの辞書に持つ。作品の中身（セリフ・人物名・あらすじ）は画面の文言ではないので、作品の言語の版（2.3）で別に持つ。
- 対象の言語は、日本語と英語の2つだけ（利用者の決定 2026-10-09。前は今のアプリと同じ8言語としていた）。
- 辞書に無い文言を、黙って別の言語で出さない（私の判断。fallback禁止の決まりに合わせる）。
- 言語を選ぶ欄には、辞書のある言語だけを出す。選んでいなければ日本語で出す（ブラウザの言語からは決めない）。
- 文言の長さは言語で変わる。固定幅を使わない決まり（プロジェクトの決まり）は、このためにも守る。

### 24.3 `v3/web/` の作り（2026-10-09）
- 部品は i18next 26.4.2（MIT。`v3/web/vendor/i18next-26.4.2/`。npm の包みの `dist/esm/i18next.js` をそのまま置いた）。今のアプリと同じライブラリ。
- 入口は `common/i18n.js` の1か所。どの画面も、ここの `t()` だけを使う。
  - 文言は、コードに日本語のまま書いて `t("保存")` と包む。日本語は辞書を持たず、書いた文言がそのまま出る。
  - 値が入る文言は `t("{{n}}ページ", { n })`。数で形が変わる文言は `count` で渡し、辞書に `_one`・`_other` などを書く。
  - `t()` の1つ目は、文字列をそのまま書く（変数や式を渡さない）。表から引く文言は、表を作る所で1つずつ包む。
  - 文言を断片でつながない。失敗の知らせ（`fail`）には、丸ごとの文を渡す。
  - HTML に直接書いた文言は、要素に `data-i18n`（中の文字）か `data-i18n-attr`（属性）を付ける。
  - 辞書に無い文言は、頭に ⚠ を付けて出し、`console.error` に出す。
- 辞書は `i18n/<言語>/<画面のまとまり>.js`（左が日本語の文言、右が訳）。`i18n/<言語>.js` が1つにまとめる。まとまりは common・harness・imagegen・manuscript・planning（作品と話・企画・構成）・production（設定資料・書き出し・生成サービス・取り込み・翻訳・確認）。
- 言語は、帯（`common/nav.js`）の右の欄で選ぶ。選ぶと `localStorage` の `v3.ui_lang` に残し、ページを読み込み直す。`?ui=en` を付けて開くこともできる。`?lang=` と `v3.lang` は、翻訳の画面が「訳す言語」に前から使っているので、画面の言語には使わない（初めは同じ名前にしていて、翻訳の画面を英語へ訳す向きで開くと画面まで英語に替わった）。
  - 読み込み直す理由：モジュールの一番上で作る表（状態の名前・キーの操作の名前）も訳すため。描き直しの仕組みを画面ごとに持たずに済む。
- 検査は `test/i18n_check.mjs`（ブラウザは要らない。JS を読む部品は acorn 8.19.0。`test/vendor/acorn-8.19.0/`）。次を止める。
  - 日本語の文字列が `t()` に包まれていない（JS の文字列・テンプレートの地の文・HTML の文字と属性）
  - 使っている文言が辞書に無い・辞書に使っていない文言がある・訳に日本語が残る・同じ文言の訳がまとまりで違う
  - 訳さない物は、コメントの印で外す：`// i18n:data`（画面の文言ではないデータ）・`// i18n:dev`（作る人だけが見る文）・`// i18n:off`〜`// i18n:on`
- 訳していないもの
  - サーバーから来る文（API の失敗の理由、サーバーが持つ名前）は、日本語のまま出る。サーバーの側の多言語は作っていない。
  - PSD のレイヤーの名前は、書き出しと読み戻しで突き合わせるデータなので、言語で変えない。
  - 英語で表示したときに、文字がはみ出さないか・図の箱に収まるかを確かめた範囲は、`V3画面の一覧.md` の 4.1 に書く。

### 24.4 画面の試作（`v3poc/screen/`）
- 辞書は `i18n/en.js`（英語だけ）。キーは日本語の文言。値が null の文言は作品の中身で、訳さない。
- 描いた後の画面の文字を、1か所で辞書に置き換える簡易な作り。`v3/web/` の作り（24.3）とは別で、試作のためだけのもの。
- 数字や名前が入る文言（「p.8 コマ3」「2回目」など）は、辞書の下の置き換えの規則で扱う。
- 辞書に無い文言は日本語のまま残し、数を数える。

### 24.5 サーバーが返す文（2026-10-09）
- サーバーが返す失敗の文も、画面の言語で出す。画面は要求を送る1か所（`v3/web/js/api.js`）で、選んでいる言語をヘッダー `X-V3-Lang` に付ける。サーバーは、失敗の返事を作る所（`v3/server/src/v3server/http_routes/http_app_factory.py`）でだけ言語を決める。ヘッダーが無ければ日本語。
- コードには日本語の文をそのまま書いて、`m("コマ {id} には枠がまだ無い", id=…)` と包む（`v3/server/src/v3server/messages.py`）。包んだ物は文字列の一種で、中身は日本語の文そのもの。日本語で出すときの文は、包む前と1文字も変わらない。元の文と値を持ち続けるので、返事を作る時に訳せる。
- 訳は `v3/server/src/v3server/message_catalog/en/<まとまり>.py`。キーは日本語の文（画面の辞書と同じ考え方）。辞書に無い文は、黙って日本語で出さず、頭に ⚠ を付けて出す（24.2 と同じ理由）。
- 対象は、返事を作る時に決まる文。失敗の返事：操作の失敗（V3 の失敗の型）、`HTTPException` の文、入力の確かめ（pydantic）の中でこちらが書いた文。成功の返事：返す dict・list の中に入れた `m()` の文（画像生成の処理・項目・選択肢・まとまりの名前、工程の名前、通知の種類の説明、閾値の一覧の意味、入稿前の確かめの結果、接続を試した結果の理由、AIの関与の作業の名前、締切の見込みの理由）。型の違いなど pydantic が作る文は英語のまま返る。
- API の関数に返す型（`-> dict` や `response_model`）を書かない。書くと pydantic が `m()` の文を普通の文字列に直してから渡すので、訳せなくなる（試験で止める）。途中で `str()`・f 文字列・`join`・pydantic のモデルの項目を通った文も同じ。つなぐときは `m("{head}・{tail}", …)` の形でつなぐ。
- **訳さないもの**：データベースや Temporal の記録に残してから画面に出す文（依頼の失敗の理由・工程のステップの理由と止まった理由・ネームの検査の結果・通知の題・取り消しの名前・判断待ちの理由・今のアプリの取り込みの報告・ロックの理由）。残した時の日本語のまま出る。訳すには、文の代わりに「文の番号と値」を残す形に、データの形を変える必要がある。今は決めていない（私の判断）。Temporal の流れが断った理由（工程の操作の 409）も、Temporal を通ると普通の文字列になるので日本語のまま。コードでは、こういう例外の行に `# i18n:stored`、作る人だけが見る文の行に `# i18n:dev` の印を付ける。
- 訳は日本語の文1つに1つ。「上」「左」のような短い文は、項目の名前と文の中の言葉で同じ訳になる（今は小文字）。別の訳を足すと読み込みの時に止まる。
- 訳されないまま残っているもの（2026-10-09）：画像生成の「似た別案」のよく使う値のボタン2つ（返す形が辞書のキーなので）、API の中で pydantic の検証を自分で受けて文に埋める所（外側の文だけ英語）、ネームの検査の題と結果の「吹き出し」（保存する文。コードが文字列で突き合わせている）。
- LLM に送る文（プロンプト）は日本語のまま。訳さない（プロジェクトの決まり）。
- 漏れは試験で止める（`v3/server/tests/unit/test_message_catalog.py`。fast の組）：包み方（文字列そのもの・`{名前}` と値が合う）、例外に渡した日本語の文が包んであるか印があるか、使っている文が辞書にあるか、使っていない訳・日本語が残った訳・`{名前}` の違う訳が無いか、失敗の返事が言語ごとに出るか。
