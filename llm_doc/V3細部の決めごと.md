## 1. 読む向きとページの左右

### 1.1 切り替えるのは表示位置だけ（決定 2026-09-29）
- 作品ごとに「右から」「左から」を持つ。企画の決めごとで切り替える。
- 切り替えで動くのは、ページの表示位置だけ。絵・コマ割り・フキダシは反転しない。
- 反転しない理由：反転すると、利き手・絵の中の文字・着物の合わせが逆になる。

### 1.2 向きで変わるもの
| 変わるもの | 右から | 左から |
|---|---|---|
| 1ページ目 | 左に単独 | 右に単独 |
| 見開きの組（2-3、4-5…） | 変わらない | 変わらない |
| 見開きの前のページ（2-3なら2） | 右 | 左 |
| 構成・下のページ一覧の並び | 右から左へ | 左から右へ |
| めくりのページ（見開きの後ろ） | 左 | 右 |
| ノド側の影・ノンブルの位置 | ページが左右どちらに来るかに従う | 同じ |

### 1.3 見開き1枚の絵（私の判断）
- 見開き単位で1枚の絵として持つ。どちらの半分が何ページ目になるかは、書き出しのときに読む向きで決める。
- ページごとに半分ずつ持つと、向きを切り替えたときに絵がつながらなくなる。
- 絵は反転しないので、右から読む前提で描いた見開きを左から読む作品に移すと、フキダシを読む順が逆になる。検査で見つける（1.4）。

### 1.4 検査への影響（私の判断）
- 読む順・めくりの検査は、読む向きを入力に取る。
- 左から読むときは、コマを読む順も左上から始まる。コマ割りは反転しないので、右から読む前提のコマ割りのままだと、読む順の検査で落ちる。

### 1.5 海外版
- 海外版では、この切り替えを使わない。右から読むまま、セリフを訳文に差し替える（2章）。
- 今の海外版の多くが右から読むまま出している、というのは一般的な話で、調べて確かめていない（未調査）。

## 2. 文字

### 2.1 文字の向きは読む向きと別に持つ（決定 2026-09-29）
- 縦書き・横書きは、読む向きとは別の設定。海外版は「右から読む・横書き」になるため。
- 持つ単位は言語ごと（私の判断。9章の2）。日本語は縦書き、英語は横書き、のように。

### 2.2 セリフと描き文字は絵と別に持つ（私の判断）
- セリフは絵に焼き込まず、文字として持つ。海外版は文字の差し替えだけで作れる。
- 描き文字（擬音）は、次の2つを両方持ち、1つずつ選べる。既定は「文字として置く」（私の判断。9章の3）。
  - 文字として置く：訳しやすい。手描きの勢いは出しにくい。
  - 絵の一部として描く：絵になじむ。訳すときは、残して横に訳を添えるか、消して描き直す。
- 画像生成が絵の中に文字を描いてしまったときに見つける手段は、未定。

### 2.3 言語ごとの版（私の判断）
- セリフの文字は言語ごとに持つ。フキダシの位置と話者は全言語で共通にする。
- 訳文がフキダシに収まらないときの手は、文字を小さくする・改行を増やす・フキダシを広げる、の3つ。どれにするかは言語ごとに人が選ぶ。収まらないことは検査で出す。
- 縦書きの約物（「！？」を横に並べる縦中横、長音の向き、小書きの位置）は自前で作る。描画に使うFabric.jsに縦書きが無いため（V3ハーネス設計 3.1）。

### 2.4 フォント（私の判断）
- セリフの種類（発話・心の声・叫び・ナレーション）ごとにフォントを割り当てる。
- 書き出しでフォントを画像にするときの使用許諾は、フォントごとに確認が要る（未確認）。

## 3. 媒体（決定 2026-09-29：3つとも同時に作る）

| 媒体 | 単位 | 構成の画面 | 検査で見るもの | 書き出し |
|---|---|---|---|---|
| 紙 | ページ・見開き | 見開きの並び（今の試作） | めくり・ノド・裁ち落とし | PSD・PDF |
| Webのページ型 | ページ | 見開きの並び | 見開きの使いどころ（電話の幅では見開きが1画面に収まらない） | ページごとの画像 |
| 縦読み | 1話の縦の帯 | 縦の帯に場面を並べる | コマの間の余白、1話の長さ | 決まった幅で分けた画像 |

- 試作での見せ方（2026-10-06）：企画の「媒体」を縦読みにすると、構成は場面を上から下へ並べた一覧（場面ごとの長さ付き）になり、原稿は1本の縦の帯になる。帯の左に場面の目次、帯の中に分け目の線、上の帯に全体の長さと分け目の数を出す。コマの間の余白は、場面の変わり目で広く取る。道具（選ぶ・囲んで頼む・コマ枠・ナイフ）は帯の上でもそのまま使える。Webのページ型は、紙と同じ画面を使う。書き出しで「分けた画像」を選ぶと、幅と分ける長さの欄が出る。幅800・長さ1280は例で、配信先の値は未調査。
- 縦読みには、ページ・見開き・めくりが無い。見せ場はコマの間の余白で作る、と言われる（描き方の講座は未調査）。
- 縦読みの横幅・分ける長さ・1話の長さは、配信先ごとに違う（未調査）。
- 紙と縦読みの両方に出す作品の組み替えは、手段が未定（V3ハーネス設計 18章）。
- 判型・仕上がり寸法・裁ち落とし・ノドの余白は、入稿先ごとの規定として持ち、作品はそれを選ぶ。値は未調査。
- 色（白黒2階調・グレー・カラー）はページごとに上書きできる。扉だけカラーの作品のため。

## 4. 生成サービス

### 4.1 登録するもの
| 項目 | 内容 |
|---|---|
| 種類 | 画像・文章 |
| つなぎ先 | 手元のComfyUIは送り先の住所。商用はAPIキー |
| 送り方 | 4.2 |
| 単価 | 1枚・1回あたり。人が入れる。提供元から自動で取れるかは未確認 |

- 画面は全作品で共通の「生成サービス」（上の右端の印から開く）。
- APIキーはサーバーだけが持つ（V3ハーネス設計 11章）。画面には末尾だけを出す（私の判断）。

### 4.2 送り方（決定 2026-09-29）
| 送り方 | 動き | 向く先 |
|---|---|---|
| 1件ずつ | 受けた順に1件送り、終わってから次を送る | 手元のPCのComfyUI |
| 同時に N件まで | N件まで同時に送り、あふれた分は待たせる | 商用のAPI |

- サービスごとに切り替える。サーバーの待ち行列は、サービスごとに分けて持つ。
- Nの既定値と上限は、提供元の同時実行と回数の制限で決まる（未調査）。
- 正本への書き込みは作品ごとに1本（V3ハーネス設計 9.3）。これとは別の話で、生成は並列でよい。
- 画面では、同時に走れる数を枠の数で、走っている数を塗った枠で見せる。

### 4.3 使い分け（決定 2026-09-29）
- 処理ごとに、送り先を1つ選ぶ（決定 2026-10-07。4.7）。それまでは、工程ごとに「作る」と「直す・作り直す」の2つを選ぶ形だった。
- 既定（私の判断。9章の7）：作る処理は費用の安い先、直す処理（絵から作り直す・囲んで直す）は得意さの高い先。
- 1回ごとに選び直せる。原稿の「頼む」の横の設定で選び、ボタンに送り先と費用を出す。
- 作品の「送ってよい先」（V3ハーネス設計 4.2）に無いサービスは選べない（私の判断）。
- 候補には、どのサービスで作ったかを出す。

### 4.4 待ち行列の順番（私の判断）
- 人が画面で頼んだものを先にする。AIが工程を進めるための生成は後。人が画面の前で待っているため。
- 同じ扱いの中は、頼んだ順。
- 人は、待ちの順番を入れ替え、取り消せる。
- 作品をまたぐ順番は未定（V3ハーネス設計 2.4の29）。

### 4.5 失敗したとき
別のサービスへ自動で回さない（決定：方針7）。種類ごとの扱いは次のとおり（私の判断）。

| 失敗 | 扱い |
|---|---|
| 回数・同時実行の制限 | 待つ状態にし、同じサービスに送り直す（方針8） |
| 時間切れ・通信の失敗 | 同じサービスに送り直す。回数を超えたら止めて人に知らせる |
| 内容で断られた | 記録して止め、人に知らせる。送り直さない |
| 返ってきた形が崩れている | 失敗として記録し、使わない |
| 予算の上限 | 待つ状態にする（方針8）。人が上限を上げるか、月が変わるまで待つ |

- 止まったものは待ち行列に残す。人が「もう一度」か「サービスを選んで送る」を押す。
- 工程を止めているなら、判断待ちにも入れる。
- 送り直しの回数（通信の失敗）と、作り直しの回数（出来が悪い）は別の設定にする。

### 4.6 費用
- 頼む前に、ボタンに費用を出す（単価×枚数）。文章は長さで変わるので、見込みの額になる。
- 予算は、全体の月の上限と、作品ごとの上限の両方を持つ（私の判断。9章の6）。上限の何%で止めるかを選ぶ。
- 手元のComfyUIは費用0として数える。
- 待ちを取り消したときは費用はかからない。生成中に止めたときに課金されるかは、提供元による（未確認）。

### 4.7 つなぎ先と、処理ごとの送り先（2026-10-07）
- 今のアプリの設定の窓を確かめた（`js/ai/role/ai-roles.js`、`js/ai/role/role-assignment-ui.js`、`index.html` の設定の窓）。
  - 処理10種類（文から絵、絵から絵、囲んで直す、拡大、背景を抜く、角度、絵から指示を読む2種、指示を書く、絵を文章モデルで読む）と、接続先7つの表。処理ごとに送り先を1つ選ぶ。できない組み合わせは選べない。
  - 接続先ごとに、処理ごとのモデル、同時に送る数、APIキーか住所を持つ。ComfyUIは手順を種類ごとに持つ。
  - 得意不得意と費用は持っていない。
- V3も同じ形（処理とつなぎ先の表）にし、セルに得意さと1回の費用を足す（決定：利用者の指示 2026-10-07。処理ごとに得意不得意がある、費用でこちらが良いという場合もある、これはこっち・これはあっちを決める設定画面が要る）。
- 表：行は処理（工程ごとにまとめる）、列はつなぎ先。画像と文章で表を分ける。セルには得意さ（◎得意・○ふつう・△苦手）と1回の費用を出す。セルを押すと、その処理をその先へ送る。取り消せる。できない組み合わせは押せない。
- 処理（試作の16個。私の判断）：
  - 画像：ラフを作る、人物の絵を作る、絵を作る、絵から作り直す、囲んで直す、角度を変える、顔・手を直す、白黒化・トーン、拡大、背景を抜く。
  - 文章：構成・コマ割り、セリフ、翻訳、指示を書く、絵から指示を読む、検査・評価。
- 得意さは人が付ける（私の判断）。提供元の説明や推測では決めない。判断の材料として、つなぎ先ごとの実績（採用した数と送った数、採用1つあたりの費用、平均の時間）を並べる。実績は採用・却下の記録から数える（数え方は未設計）。
- 「同じ指示で比べる」：同じ指示を、送れる先すべてへ送って見比べる。費用がかかる。試作では見た目だけ。
- 費用は、つなぎ先と処理の組ごとに持つ。同じ先でも処理で違うため。人が入れる（4.1）。
- 中身（12章）も、つなぎ先と処理の組ごとに持つ。ComfyUIは手順とモデル、APIはモデルの名前。送り直しと作り直しの回数（4.5）は処理ごとに持つ。
- 生成サービスの画面には右の欄を置かない（決定 2026-10-07。右の欄が押した場所で別物に替わり、同じ操作が中心と右の両方にあって、利用者から「直観的じゃなくてよくわからん」と言われたため）。画面は「処理ごとの送り先」と「つなぎ先」の2つのタブに分ける。
- 「処理ごとの送り先」のタブ：セルを押すと送り先が決まる。行の名前を押すと、その行の下に細かい設定が開く。開いた中は、つなぎ先の列にそろえて、得意さ・1回の費用・採用した数・採用1つあたりの費用・平均の時間・手順・モデルを並べる。その下に、送り直しと作り直しの回数、「同じ指示で比べる」を置く。
- 「つなぎ先」のタブ：つなぎ先1つを1枚のカードにする。状態、休ませる、住所かAPIキー、つながるか試す、送り方、いまの走り具合、入っているもの、止まったもの、商用利用の条件（押すと開く）。表の列の見出しを押すと、このタブのそのカードへ移る。
- つなぎ先：手元（ComfyUI、手元の文章モデル）とAPIを、同じ形で並べる。違いは、つなぎ先が住所かAPIキーか、費用が0かどうかだけ。
- つなぎ先ごとに状態を持つ：つながっている・止まっている・キーが通らない・未確認・休ませている。列の見出しの印で見せる。
- 休ませる：人が手で止める。手元のPCを別の用途に使うときのため。休ませた先へ頼んだものは待ちに入り、戻すと順に送る。
- 組：送り先の全体を1回で切り替える。安く・得意を優先・手元だけ・APIだけ。送れる先だけから選ぶ。選べる先が無い処理は変えずに、そのことを知らせる。切り替えるのは人で、自動では切り替えない（方針7）。
- 送れない先を使っている処理があるときは、上の帯の待ち行列の印と、頼むボタンと、表のセルに出す。頼んだものは待ちに入る（4.5）。
- 手元のComfyUIは、入っているモデル・追加学習・手順の数を読み直せる。手順に要るモデルが無いときは印を出す。ComfyUIから一覧を取る口は、V3では未検証。
- 止まったもの（4.5）は、つなぎ先のカードに出す。「もう一度」と「先を選ぶ」。
- 試作で動くもの：セルを押して送り先を変える・取り消す、得意さを付け直す、組の切り替え、つながるか試す、休ませる。見た目だけのもの：つなぎ先を足す、読み直す、同じ指示で比べる、もう一度、いまの並びを組に残す、費用と中身の欄。
- 試作のつなぎ先の名前は、今のアプリにある接続先の名前を借りた（文章の1つはV3の試作で使っているもの）。得意さ・費用・実績の数字はすべて例で、調べた値ではない。
- 未決：作品ごと・人物ごとに送り先を変えられるようにするか（12章の「決まる順番」との関係）。

## 5. 判断待ち

### 5.1 番号と印（試作で採用）
- 番号は全画面で1本。前後の送りも、全画面を通して回る。
- 印の形：判断待ちは橙の丸、検査の失敗は赤の角丸、人の書き込みは書いた人の頭文字。
- 赤は検査の失敗だけに使う。赤入れの線そのものは赤のまま。

### 5.2 並び（私の判断）
- 工程の前のものから（構成→設定資料→ネーム→作画→仕上げ）。
- 同じ工程の中は、後ろの工程を止めている数が多いものから。

### 5.3 採用・却下・取り消し
- 採用のボタンの上に、捨てるもの（描き直しになるページ）と、残っている失敗を出す（試作で採用）。
- 却下は止まるだけ。作り直しは、人が「頼む」で指示する（私の判断）。自動で作り直す設定も持つ（9章の4）。
- 理由：理由を付けずに作り直させると、前と同じ物が出るのではなく、前から大きく離れる。直してほしい所と関係なく変わる（2026-10-08 に根拠を改めた）。
  - 試作 p30（一覧 6-4、`V3検証の結果.md`「6-4 理由なしの作り直し」）：LLM に作画用の言葉を作らせ、却下だけを伝えて作り直させた。前の言葉との重なりは、理由なし 0.374・理由あり 0.46。理由なしの作り直しどうしは 0.524 で似た。
  - もとの根拠「理由が分からないまま作り直すと、同じ物が出やすい（推測）」は、この結果と逆だったので外した。
  - 理由ありの作り直しが、指摘した所を直せたかは測っていない。絵での比較も未検証。
- 採用・却下は取り消せる。取り消したとき、その後に進んだ後ろの工程は消さず、「古い」印を付ける（私の判断）。

### 5.4 上流を変えたときに古くなるもの（私の判断）
| 変えたもの | 古くなるもの |
|---|---|
| 企画 | 構成すべて |
| 構成（ページの割り当て） | 割り当てが変わったページのネーム以降 |
| 設定資料（キャラの決まり） | そのキャラが出るコマの検査結果 |
| ネーム | 変わったコマの作画以降 |
| 作画 | そのコマの仕上げ |

- 古くなったものを自動で作り直すかは、企画の「AIを止める所」に従う。既定では自動で走らせない（自動で走る機能は設定で切れるようにする、という以前からの決まり）。
- 人が直した所（確定印、V3ハーネス設計 9.2）は、古くなっても自動で上書きしない。
- 設定資料を変えたときは、絵を作り直さず、検査だけをやり直す。

## 8. 画面の決まり

### 8.1 色の組（決定 2026-10-08）
- 色は、あとで組ごと替えられるようにする。今ある組は「砂漠」だけで、組を選ぶ画面と、ほかの組は作らない（利用者の指示）。
- 決まりは `v3/web/common/theme.css`。値は持たず、色の名前と意味だけを書く。値は `v3/web/common/themes/desert.css` が持つ。使う組は `theme.css` の末尾の `@import` の1行で決める（ここ1か所）。
- 画面の CSS と JS は名前（`var(--名前)`）だけを使い、色の値を書かない。原稿・工程の画面も同じ。
- canvas に描く色（囲んだ範囲・人の手の範囲・ペンの先）は、`v3/web/common/theme_colors.js` の1か所で `getComputedStyle` から読む。名前が無ければ止める（代わりの色で描かない）。工程の図（Cytoscape）は `harness/harness_graph.js` が同じやり方で読む（Cytoscape は CSS の変数も `color-mix()` も読めないので、要素の色に当ててブラウザに解かせる）。
- 試験：`node v3/web/test/theme_check.mjs`（ブラウザは要らない）。組のファイルの外に色の値（`#…`・数の入った `rgb()` など・`white` などの名前）が無いことと、どの組にも決まりの名前が全部あることを確かめる。今は名前 52 個、色の値 0 件。
  - 決め打ちを許すのは、行に `色の決め打ちを許す：理由` と書いた所だけ。今は、画像生成のペンの墨（`#000000`。描いた線は絵のデータになる）・囲んだ範囲を書き出すときの白（マスクの値）・企画の色の欄に入力の形の例として薄く見せる文字（`#000000`）。
  - ファイルごと許すのは `manuscript/js/print_colors.js` だけ。理由：原稿のデータとして刷る黒と紙の白で、書き出しにそのまま入る。画面の色の組を替えても変えてはいけない。
- 組を足すとき：`themes/<名前>.css` を作り、決まりの名前を全部書く（紙の物 `.paper,.cand` の中で替える名前も）→ `theme.css` の `@import` の1行を替える → `theme_check.mjs` を流す。
- 名前（意味は `theme.css` に書いた。ここは一覧）：

| 種類 | 名前 |
|---|---|
| 地 | `--bg` `--canvas` `--dot` `--surface` `--surface-2` `--surface-3` `--on` `--raise` `--glass` |
| 線 | `--line` `--line-2` |
| 文字 | `--ink` `--ink-2` `--ink-3` `--ink-4` |
| 印 | `--ai` `--ai-ink` `--ai-tint` `--ai-line` `--need` `--need-ink` `--need-tint` `--need-line` `--bad` `--bad-ink` `--bad-tint` `--bad-line` `--ok` |
| 仕事の状態 | `--st-wait` `--st-run` `--st-done` `--st-fail` |

## 10. 人が直接描く・直す（私の判断）

### 10.1 道具（試作で採用）
- 原稿の上の帯に、AIに頼む道具（選ぶ・囲んで頼む・赤入れ）と、人が描く道具（ペン・消しゴム・文字・コマ枠・ナイフ・フキダシ・トーン・図形・手のひら）を並べる。その右に、読む順・表示するもの・取り消す・やり直す・拡大縮小を置く（2026-10-06 に追加）。
- ナイフ：コマを押した所で2つに分ける。向きは横・縦・斜めを選ぶ。斜めは角度を決める。切る線は、押す点を通る1本の線として、押す前から見える。分けた間の幅は「コマの間」で決める。絵は大きい側に残り、分けた2つのコマに人の手の印が付く（10.2）。細すぎる分け方は受け付けない。斜めに切ったコマは四角でない形になり、もう一度切ることも合わせることもできる。
- トーン：網点・線・砂目・グラデ・雪・集中線・スピード線。線数・濃さ・角度と、貼る所（コマ・囲む・塗る）を選ぶ。
- 図形：絵記号を探して置く。線・塗り・影を決める。
- 手のひら：原稿を掴んで動かす。
- コマ枠：枠の線を掴んで動かす。線を引いて1つのコマを分ける。隣の2つを合わせる。合わせるときは、コマ枠の道具で「合わせる」を選び、2つを順に押す。2つを包む1つの形になり、中身は大きい側のものが残る。隣り合っていない2つは受け付けない。
- フキダシ：動かす・大きさを変える・しっぽの向きを変える・形を変える。セリフは、フキダシを2回押して、その場で打つ。
- 文字：写植と描き文字を置く（2.2）。
- ペン・消しゴム：人の手の層に描く。消しゴムはAIの絵の層にも効く。消した跡は人の手として扱う（10.2）。

### 10.2 人が直したところを守る
- 人が描いた・動かした・消したところに「人の手」の印を付ける。
- AIに作り直させるとき、人の手の範囲は描き直す範囲から外す。
- 人の手の印を外せるのは人だけ。
- 理由：AIが人の直しを上書きすると、同じ直しを2回することになる。
- 描き直す範囲から外す仕組みが、ComfyUIで狙いどおりに効くかは未検証。

### 10.3 1ページの層
- 下から、紙（白）、コマごとの絵（グループ。コマの地・コマの絵・層）、トーン・図形、コマ枠、人の手、フキダシ、写植、描き文字の順に重ねる（2026-10-08 に変更）。
- コマ枠をコマの絵より上に置く。理由：試作 p59 で、枠を絵の下に置いた PSD は、絵の不透明な所が枠を隠し、枠の線の 49.8% が見えなかった。
- 紙の層を一番下に置く。理由：紙が無いと、PSD を開いた道具によって、透明な所の見え方（白か市松か）が変わる。
- どの層の名前も「名前 [id]」で終わる。id は正本の行の id か、ページ・コマの id に「-paper」などを付けたもの。PSD を戻すとき、この印で層と行を結び付ける（Krita が名前の後ろに足す NUL と、GIMP が足す「 #1」は外して読む）。
- ペンの線は、線のデータ（点の並び・筆・太さ・色）が正本。人の手の層の絵は線から作った控えで、画面（ブラウザ）が描いてサーバーへ上げる。理由：今のアプリの筆（fabric.js）を画面が持っているので、見えている絵と控えが同じになる。控えには、どの線の版から作ったかを残し、古い控えはAIへ渡す絵にも書き出しにも使わない。
- PSDの書き出しでは、この層ごとに分ける（7章）。ペンの線はPSDでは画素の層になる（線のデータはアプリに残る。PSD から線には戻らない）。書き出しの画面にもそう書く。
- 人が直したPSDを戻すとき、画素の変わったコマの絵・層は新しい版（人が手を入れた絵）にする。線や形から描いた層（コマ枠・フキダシ・トーン・図形・線の控え）と文字の層の画素が変わったとき、どの物にも当たらない層、無くなった層は、判断待ちにして人が選ぶ（文字は、打ち直す・絵として採る・捨てる）。

## 11. ネームを作画へ引き継ぐ（私の判断）
- 作画に渡すもの
  - コマの形と大きさ
  - ネームの人物の位置と姿勢（範囲の指定か骨格の図にして渡す。下に理由）
  - 出る人物の設定資料
  - セリフ（文字は絵に描かせない。ハーネス設計 8.1）
- 作画に渡さないもの
  - ネームの線そのもの（棒人間の線画）
  - フキダシの位置
- 人物の位置と姿勢の渡し方（2026-10-08 に改めた。根拠は `V3検証の結果.md` 1-25、試作 p08）
  - ネームの線を構図の下絵として渡すのはやめた。棒人間を線画の制御（t2i-adapter-sketch-sdxl、sai_xl_sketch_256lora）に渡すと、人物の枠とラフの重なり（IoU）は制御なしと同じ 0.13 前後で、棒人間がそのまま絵に描き込まれた。
  - 効いたのは、範囲の指定（その範囲に人物の文を当てる。0.67）と、骨格の図（thibaud_xl_openpose。0.63）。2つを重ねると 0.39 に下がり、人物が崩れる・透ける絵が出た。どちらか一方を使う。骨格の図でも t2i-adapter-openpose-sdxl は骨格を無視した（0.24）。
  - 試したのは立ち姿1種だけ。座る・走るなどの姿勢では未検証。ネームの線から範囲や骨格の図を作る処理も、まだ作っていない（未検証）。
- フキダシの位置を渡さない理由（2026-10-08 に改めた。ハーネス設計 8.1 と同じ）
  - フキダシと文字は画像生成で描かず、仕上げで絵の上に置く（ハーネス設計 8.1・17章の8）。
  - 1-25 では、どの渡し方でもフキダシの場所に背景が描き込まれ、空かなかった。渡しても空けられないので、渡さない。

## 22. ショートカットキー・全画面・絵だけ（試作で採用。共通の部品にした 2026-10-08）

### 22.1 決まり
- キーを押すのは、画面のボタンを押すのと同じにする。キーのための処理を別に作らない（1か所で押す）。
- ボタンに指を置くと、そのボタンのキーが出る。ボタンの `<kbd>` と `title` は、割り当てから書く（`data-key="操作の名前"` を付けたボタン。キーを変えるとすぐ書き直す）。
- 描く道具のキーは、Photoshopと同じ割り当てにする（V・B・E・T）。
- 割り当ては、利用者ごとに変えられる（22.4）。

### 22.2 キーの割り当ての作り（共通の部品）
- 全部の画面の割り当ては1つの一覧 `v3/web/common/key_catalog.js` に書く。1件は「操作の名前・どこで効くか・名前・キー」。画面のコードは、操作の名前に処理を結ぶだけ（`km.bind("workbench.pen", …)`）。キーを受けるのは `v3/web/common/keymap.js` の1か所。
- どこで効くか（scope）は3段：道具（`画面:道具`。例 `workbench:mask`）→ 画面 → どの画面でも（`global`）。同じキーなら狭い方が先に効く。
- 同じキーを、わざと重ねてよい物がある（`chain`）。Esc・Tab・矢印。狭い方の処理が「することが無い」と返すと、次の物へ回す。Esc はこれで「道具の途中をやめる → 画面の物を閉じる → 絵だけから抜ける → 全画面から抜ける」の順に1つずつ抜ける。
- 押している間だけ効く物（`hold`）：Space（手のひら）。離すと元の道具に戻る。ブラウザの窓から外れたときも離したことにする。
- 続けて押すキー：「G のあと 1」のように、1秒の間に2つ押す。
- Ctrl と ⌘：割り当ては `$mod` と書き、Mac では ⌘、ほかでは Ctrl にする（`navigator.platform` で見分ける）。Mac の Option は文字を変える（⌥+L が ¬ になる）ので、キーを変えるとき Option と組んだキーは位置（`e.code`）で残す。
- 文字を打っている間（入力の欄・文の欄・`contenteditable`）は、画面のキーは効かない。そこで効くのは、印を付けた物だけ：Esc（欄から出る）と Ctrl+Enter（頼む）。
- IME の変換中は、どのキーも効かない。`KeyboardEvent.isComposing` か `keyCode` が 229 の物を捨てる（MDN の KeyboardEvent.isComposing の説明と同じ扱い。https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing ）。
- 開いている窓（`dialog`）の中のキーは、その窓が受ける。閉じた窓の入力の欄に入ったままのキーは、欄から出して画面のキーとして受ける（Chromium で、Esc で閉じた直後に入ったままのことがあり、キーが全部止まっていた。試験で見つけて直した）。
- キーを受ける部品は tinykeys 3.0.0 を `v3/web/vendor/tinykeys-3.0.0/` に置いて使う（MIT。https://github.com/jamiebuilds/tinykeys ）。選んだ理由：`$mod` で Ctrl と ⌘ を替える書き方と、続けて押すキーの書き方を持ち、650バイトほどで小さい。キーの書き方を読む所（`parseKeybinding`）と、押したキーが合うかを見る所（`matchKeyBindingPress`）だけを使い、どれを先に効かせるか・重ねる・押している間は自分で書いた（tinykeys の受け口は合う物を全部呼ぶので、狭い方を先にできない）。tinykeys は修飾キーを厳しく見るので、`?` と `+` は `Shift+?`・`Shift++` と書く（`+` は Shift 無し（テンキー）と有りの2つを持つ。見せるときは1つにまとめる）。

### 22.3 キーの一覧
- `?`（Shift+?）か、画面の帯の「キー」で出す。今の画面と今の道具で効く物を、効く順（道具 → 画面 → どの画面でも）に並べる。結んである物だけを出す。
- 上の欄で、名前とキーの両方から探せる。
- 印：押している間・この画面にまだ無い（キーは空けてあるが機能が無い）・変えた。
- 窓の下に、Mac のキーと IME の決まりを書く。電話の幅では、帯の「キー」の文字を隠し、印だけ出す。

### 22.4 キーを変える（利用者ごと）
- 画面の帯の「キー」→「キーを変える」か、キーの一覧の「キーを変える」から開く。全部の画面の割り当てを出し、今の画面を先に並べる。
- 1件ごとに「足す」（押したキーを録る。Esc でやめる。押している間の物は Alt などの修飾キーだけも録れる）・キーを外す・「初めに戻す」。
- 重なり：足そうとしたキーが、同じ所で効く別の物と重なると、窓の中に赤い知らせを出して、まだ残さない。「相手から外して割り当てる」か「やめる」を選ぶ。重なりの判定：効く所が同じか、どちらかが「どの画面でも」か、片方がもう片方の道具の段か、で、文字を打っている間かどうかも重なり、どちらも `chain` ではなく、キーが同じか、続けて押すキーの頭が同じ。一覧の上には、今の割り当て全部の重なりを出す（初めの割り当ては 0 件。試験で確かめる）。
- 全部を初めに戻す（確かめてから）。
- 今のアプリのキーを読み込む：今のアプリで違うキー（F1・Ctrl+8・Ctrl+9・Ctrl+0・Alt+←→ など）を並べ、読み込むと足す（V3 の初めの割り当ては消さない）。V3 に無い物（Ctrl+G など）は理由と一緒に並べるだけ。
- 残す所：サーバーの利用者ごとの設定 `GET/PUT /me/settings` の `other.keymap`（`{操作の名前: [キー]}`。初めと違う物だけ）。PUT は全部を書き換える口なので、読んでから `language`・`autosave`・`autosave_interval_seconds` と `other` のほかの値をそのまま付けて送る。ほかの端末でも同じ割り当てになる。localStorage には残さない。
- 読めないとき・利用者の名前が無いときは、初めの割り当てで動き、キーの一覧とキーを変える窓に「…初めの割り当てで動いています」と出す（黙って代わりの物を使わない）。

### 22.5 全画面と絵だけ
- 2つを分ける：
  - 絵だけ（Shift+F）：ページの中で、パネルを隠して絵の所を広げる。ブラウザの帯は残る。
  - 全画面（Ctrl+Shift+F・⌘+Shift+F）：ブラウザの Fullscreen API（`requestFullscreen`）で画面いっぱいにする。
- 画面ごとの絵だけ：
  - 原稿：絵（ページ）だけ。道具の帯は残す。
  - 画像生成：絵と、下に候補の帯（候補だけを横に並べる）。道具の帯は残す。
  - 工程：図だけ（見張る画面として使う）。図の色の説明と「全体を見る」は残す。パネルが出入りしたら図の大きさを合わせ直す。
  - 確認：「読み通す」。ページを大きく1枚ずつ出し、矢印は作品の読む向きに合わせる（右から左の作品では ← が次）。PageDown・PageUp は向きによらず次・前。ページの絵を返す口がまだ無いので、番号・状態・コメントを出す。
  - 作品をまたぐほかの画面（作品と話・企画・構成・設定資料・書き出し・生成サービス・取り込み・翻訳）：上の帯と画面の帯を隠す。
- Tab：絵だけのとき、パネルを一時的に出す・隠す。絵だけでないときは、Tab は普通の移動のまま。
- 右下に小さい帯（パネル・全画面・抜ける）を出す。キーを知らない人もマウスで戻れる。
- Esc の順：道具の途中 → 絵だけ → 全画面。全画面のとき Chromium では Keyboard Lock（`navigator.keyboard.lock(["Escape"])`）で Esc をページが受ける。このとき Esc を長く（2秒）押すとブラウザが全画面を抜ける（WICG の Keyboard Lock の決まり。https://wicg.github.io/keyboard-lock/ ）。Keyboard Lock の無いブラウザでは、1回目の Esc でブラウザが全画面を抜ける（未検証。Chromium 以外では確かめていない）。
- ブラウザの側で全画面を抜けたとき（Esc・F11・ブラウザのボタン）は `fullscreenchange` を受けて、画面の印を合わせる。絵だけはそのまま残る（試験で確かめた）。
- 覚える：絵だけかどうかは画面ごとに、このブラウザの localStorage `v3.view.<画面>` に残す（見た目の好みなので、サーバーには残さない）。全画面は開き直したときに戻さない（ブラウザが、人の操作なしの全画面を許さない）。
- 状態は `<html>` の `data-focus`・`data-peek`・`data-fullscreen` で見せ、隠すパネルには `data-v3-panel` を付ける（CSS の1か所 `common/keys.css` で隠す）。変わると `window` に `v3-view` の出来事を送る。

### 22.6 ポインタ
- 修飾キー（Ctrl・⌘）+ホイール：広げる・縮める。ホイールだけ：上下に動かす。Shift+ホイール：左右に動かす。原稿の画面と同じにした（画像生成の画面は、ホイールだけで広げていたのを改めた 2026-10-08）。
- Space+ドラッグ：手のひら（押している間）。
- タッチの2本の指で広げる：トラックパッドの2本の指はブラウザが Ctrl+ホイールとして送るので、上と同じに効くはず（未検証。実機で確かめていない）。タッチの画面の2本の指は、まだ作っていない。
- ペンの横のボタン：まだ作っていない（未検証。ブラウザの `pointerdown` の `button` で見分けられるかを確かめる）。
