# 次期サーバー化計画

2026-08-29〜31の実測から出てきた、アプリの土台をどうするかの判断材料。

**これは決定ではない。** 現行の `CLAUDE.md` は「`file://`プロトコルで動作必須」を掲げており、
本ドキュメントはそれを変えるかどうかを判断するための材料を並べたもの。
実測した事実と、まだ確かめていないことを分けて書く。
数字の出典と再現手順は `ai-verification.md`（特に4章・4b章）にある。

---

## 1. なぜこの話が出たか

AI機能の追加案を検証する過程で、**壁になったものがほぼ全部 `file://` 由来**だった。
同時に、ブラウザ内推論を実測したところ **ComfyUI経由より20〜40倍速い**ことが分かり、
「どこで計算するか」の前提が変わった。

### 1.1 ブラウザ内推論の実測（WD14タガー 311MB、1枚あたり）

| 実行環境 | ロード | 1枚あたり |
|---|---|---|
| **ブラウザ webgpu**（`file://` / classic Worker） | 0.9s | **53 ms** |
| ComfyUI経由（GPU） | — | 1,000〜2,000 ms |
| ネイティブCPU 全コア（python onnxruntime） | 1.2s | 950 ms |
| ネイティブCPU 1スレッド（同上） | 1.4s | 2,039 ms |
| ブラウザ wasm 1スレッド | 1.7s | 6,093 ms |

同じGPU（NVIDIA Lovelace）。別々に作った2枚のページで再現している。

**ComfyUIの1〜2秒は、HTTP往復・画像アップロード・キュー・ノード処理が大半だった。**
モデルの計算自体は50ms程度。ブラウザから直接叩くとその往復が消える。

意味するところ:

- **検査系（タグ・顔検出・キャラ同一性・OCR）は ComfyUI が要らなくなる。**
  生成のたびに回しても体感に出ない
- **生成そのものは引き続き ComfyUI が要る。** SDXLの重みをブラウザに載せる話ではない
- **wasm（CPU）には使い道が無い。** ネイティブCPU1スレッドの3倍遅く、ComfyUI経由より遅い。
  WebGPUが使えない環境では、この用途は成立しない
- 小さいモデルでは逆転する（`face_landmark` 2.7MB は wasm 9ms / webgpu 13ms）。
  **モデルの大きさで選ぶ必要がある**

## 2. `file://` が課している制約（実測）

`ai-verification.md` 4章・4b章の要約。**「動く」と「動かない」を対で書く。**

### 2.1 動かないもの

| 項目 | 影響 |
|---|---|
| `fetch()` でのローカル読み込み | **モデルもランタイムも読めない。** 配布方法が縛られる |
| 隣に置いた `.mjs` の動的import | ESM配布のライブラリがそのまま使えない |
| `<script type="module" src>` | 同上 |
| `{type:"module"}` の Worker | classic Worker で代替が要る |
| `getImageData`（`file://` の画像） | SecurityError。canvasが汚染される |
| `SharedArrayBuffer` / `crossOriginIsolated` | WASMのマルチスレッド不可（`numThreads=1` 固定） |
| ServiceWorker | 登録できない |
| **Chrome拡張（Claude in Chrome）** | **ページを一切操作できない。** 開発時のUI確認が手動になる |

### 2.2 動くもの

| 項目 | 備考 |
|---|---|
| classic Worker（Blob URL） | **裏スレッドは使える** |
| `blob:` / `data:` URL のモジュールを動的import | `.mjs` の回避策として成立 |
| `blob:` モジュールの中から別の `blob:` を import | 入れ子も通る |
| base64からのWASM実体化 | `third/lz4/` と同じ方式 |
| **WebGPU** | Workerの中からも `navigator.gpu` が見える |
| IndexedDB（localForage） | オリジン単位 |
| `importmap` | 対応 |
| `getImageData`（`data:` URLの画像） | 本番で10箇所以上稼働中 |

### 2.3 いま採っている回避策

ブラウザ内推論を `file://` で通すために必要なもの。**実測で動作を確認済み。**

1. ORT本体は classic script（`ort.min.js` / global `ort`）を `importScripts`
2. Emscriptenグルーの `.mjs` を**文字列から `blob:` URL 化**して `env.wasm.wasmPaths = {mjs: url}`
3. `.wasm` 本体を `env.wasm.wasmBinary` に ArrayBuffer で直接渡す（fetchさせない）
4. モデル（311MB）は `<input type="file">` で選んでもらい、IndexedDBに保存して使い回す
5. 大きいモデルは `File` のまま Worker へ渡し、**Worker側で `arrayBuffer()` する**

5を守らないと落ちる。311MBのArrayBufferと37MBのランタイム文字列を一緒に `postMessage`
したところ、Workerが静かに死んだ（`onerror` も鳴らない）。

## 3. サーバー化すると何が解けるか

ローカルにHTTPサーバを立てて配信する形にした場合。

### 3.1 解けるもの

- **`fetch()` が使える。** モデルもランタイムも普通に読める。
  ファイル選択とIndexedDBの仕組みが要らなくなる
- **ランタイム27MBをリポジトリにbase64で載せる必要がなくなる**（約37MBの削減）
- **ESMがそのまま使える。** `blob:` URL化の回避策が要らない。
  ESM専用配布のライブラリが選択肢に入る
- module Worker が使える
- COOP/COEPヘッダを付ければ `SharedArrayBuffer` が有効になり、WASMのマルチスレッドが使える
  （ただしWebGPUの方が速いので、この用途では重要度は低い）
- ServiceWorker が使える（オフラインキャッシュ、正しいMIME）
- `getImageData` の汚染が起きない。ローカル画像を素直に読める
- **開発時にChrome拡張でUIを自動確認できる。** 今は毎回手動で開いてもらう必要がある

### 3.2 解けないもの

- **ComfyUIとの往復コストは変わらない。** 1〜2秒のうち大半はHTTP往復・アップロード・
  キュー・ノード処理で、配信方法とは無関係
- **生成の遅さは変わらない。** 指示編集の5〜6分はモデルの問題
- WebGPUが使えない環境の問題は残る

### 3.3 失うもの

- **「ダウンロードして index.html を開くだけ」が失われる。** 起動手順が必要になる
- 配布形態を決め直す必要がある（起動用のexe/バッチ、または Node などの前提）
- `CLAUDE.md` の必須要件（`file://` 動作）の変更。既存の設計判断が広範囲に紐づいている

---

## 4. 結論として、サーバー化は必須ではない

**今回検証した方法は全部 `file://` で成立している。**
ブラウザ内推論も、WebGPUも、Workerも動く。サーバー化しなくても機能は作れる。

変わるのは**コストの置き場所**である。

| | `file://` のまま | サーバー化 |
|---|---|---|
| 利用者の起動 | 開くだけ | 起動手順が要る |
| モデルの受け渡し | 一度ファイル選択 → IndexedDB | 自動 |
| ランタイム | リポジトリに約37MB（base64） | 普通に配置 |
| ライブラリの選択肢 | classic/UMD配布のものに限られる | 制限なし |
| 開発時のUI確認 | 手動で開いてもらう | 自動化できる |

**判断の分かれ目は「利用者に起動手順を課すか」の一点。**
技術的な障害はすでに無い。

## 5. AI機能の工程計画

部品ではなく工程として並べた場合の依存関係。詳細な一覧は別途アーティファクトにある。

### 土台

| | 内容 | 状態 |
|---|---|---|
| **A** | **ページ工程**（やることを並べて一括で流す） | Queueの永続化が前提。下記5.1 |
| **B** | **話者と、吹き出し⇄コマの紐付け** | どちらも存在しない。作る必要がある |
| **C** | **ブラウザ内推論の土台** | 動作確認済み。2.3の手順で通る |

Aが無いと 4・5・7・12 が単発のボタンで終わる。
Bが無いと工程Dで読み取ったセリフを戻す先が無く、口調チェック系も全部止まる。
Cに載せると検査系がすべて50ms級になり、ComfyUI依存が外れる。

### 大きい工程

**D: 既存の漫画を読み込んでフル再生成。** 射程は「絵柄だけ差し替える」
「白黒をカラーに」「他言語版を作る」まで届く。

| 工程 | 状態 |
|---|---|
| ページ画像 → コマ分割の検出 | 成立する。MagiV2で1ページ約1.3秒。**ただしCUDA必須・モデル3.9GB。ブラウザ内には載らない** |
| 吹き出しの検出 | 成立する。YOLOv8mで1ページ約0.12秒・モデル50MB。種別7分類も出る |
| セリフのOCR | 成立する。manga-ocrで1ページ約1.3秒・モデル116MB。縦書きはモデル側が対応 |
| タグ抽出 → プロンプト化 | 実測済み。ブラウザ内 53ms |
| 生成 → コマへフィット | 実測済み |

**前半2つの答えは「成立する」。ただしコマ分割の検出だけはGPUが要る。**
吹き出し検出とOCRはサイズ上ブラウザ内に載る見込みがあるが、ONNX変換の可否は未検証。

前半3つは `manga-scenario-builder` に実装済みのものを使う（2026-08-29 調査）。
**実施計画は `llm_doc/Manga2Manga計画.md` にある。** 解析側・描画側の調査結果もそこに置いた。

### 5.1 TaskQueue は永続化していない（2026-08-31 確認）

`js/ai/queue/task-queue.js` は135行で、`this.queue` の配列と Promise、
`_running` の Map だけで動いている。**保存も復元も無い。リロードで積んだものは全部消える。**

工程Aは1コマ5〜6分×ページ分＝数時間になるため、**ここが最初に必要になる。**
`localForage` は既にプロジェクトで使っている（`workflowStorage_local` ほか）。

## 6. 決めること

1. **サーバー化するか。** 判断の分かれ目は「利用者に起動手順を課すか」（4章）
   → **進める（決定 2026-10-07、利用者の指示）。** 今のアプリは `file://` のまま残し、V3を別のアプリとしてサーバーで作る。
   土台は `llm_doc/V3サーバーの土台.md`
2. **ランタイム27MBの置き場所。** リポジトリに約37MB（base64）で載せるか、
   モデルと同じくファイル選択にするか。サーバー化するなら消える論点
3. **着手順。** 手を止めずに1つ進めるなら 6（Upscalerの繋ぎ込み）、
   効果を取るなら A → C

## 7. まだ確かめていないこと

- **WD14のタグの中身が正しいか。** 速度計測は `Float32Array.fill(0.5)` の定数入力で行った。
  計算量は同じだが、出力の妥当性は見ていない。画像の前処理（448x448・チャンネル順・正規化）
  を合わせて、ComfyUI経由の結果と突き合わせる必要がある
- GPUメモリが少ない環境で 311MB が載るか
- WebGPUが使えない環境でどうするか。wasmフォールバックは6秒かかるので**実質使えない**
- 工程Dの解析の出力品質。パイプラインの構造とログは読んだが、**走らせて結果の妥当性を見ていない**
- ページ診断（12）の指摘が実際に役に立つか。既存ページ10枚で
  「直したいと思った指摘」の割合を測るのが先
- メインスレッドでのORT実行可否。Worker内では動くことを確認済みだが、
  メインスレッド側は測定手順の不備で未確定（実運用ではWorkerで動かすので影響は無い）
