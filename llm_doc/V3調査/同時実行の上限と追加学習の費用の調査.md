## 1. 結論

### 7-6 「同時にN件」の既定と上限

- **提供元の制限は、3種類の形に分かれる。Nの決め方も3通りになる。**
  - 同時に処理される件数そのものを制限する：fal.ai（新規2件、買い足すと最大40件）、Black Forest Labs（既定24件、flux-kontext-max は6件）
  - 1分あたりの回数と量を制限する：Anthropic、OpenAI、Google、Replicate（作成は毎分600回）、Stability AI（10秒に150回）
  - 公式には上限がなく、推奨だけがある：Runware（2〜4件）
- **画像生成の既定Nの候補は、取得できた範囲では 2〜4。**
  - fal.ai の新規アカウントが2件、Runware の推奨が2〜4件。これより小さく始めれば、どの提供元でも超えない。
  - 大きいNは、利用者が提供元の画面で自分の上限を確かめて上げる値にする。
- **上限を超えたときの返り方は、提供元で違う。**
  - 429 を返す：Black Forest Labs、Anthropic、OpenAI、Google（費用上限の場合）、Replicate、Stability AI、Runware
  - 待たせて処理する：fal.ai（待ち行列を使うと自動で並ぶ。直接呼ぶと429）
  - 待ち時間の指定（`Retry-After`）が取得できたもの：Anthropic、OpenAI、Runware。Replicate は返事の本文に「約30秒でリセット」と書かれる例があり、`Retry-After` はページに無い。Black Forest Labs は「前の依頼が終わるまで待つ」とだけ書かれ、指定は見つからなかった。
- **手元のComfyUIは1台につき1件ずつ処理する。** 取得した `main.py` の記述では、実行する作業が1本のスレッドで、待ち行列から1件取り出して実行し終えてから次を取る。同時に走らせるには、GPUごとにComfyUIを別に立てる（検索の要約）。V3の「手元は1件ずつ」と合っている。
- **見つからなかったもの**：Google の画像モデル（Gemini の画像、Imagen）の回数の数字、NovelAI の公式の制限、OpenAI の画像モデルの回数（RPM）、Stability AI の現行ドキュメントの制限（古い知識ベースの記事のみ）。

### 7-7 追加学習の時間と費用

- **手元の12GB（RTX 4070 Ti 相当）のSDXL学習の時間は、条件を明記した実測が見つからなかった。** 「未検証」とする。
  - kohya の公式文書は、SDXLのLoRA学習は12GBでできると書く。時間の記述は無い。
  - 見つかったのは、条件の無い一般的な目安（500〜2000ステップで15〜60分）と、別のGPU（RTX 3060 12GB）での他人の報告（4000〜5000ステップで3〜5時間）だけ。
- **クラウドの代行サービスは、1回あたり約 $0.6〜$2 の範囲（Civitai は Buzz 建て）。SDXL専用の公式の料金は、fal.ai と Replicate では見つからなかった。**
  - Civitai の画面上の学習（SDXL）：初期値の2000ステップ・10エポックで 500 Buzz。1ステップ0.3〜0.5秒、2000ステップで5〜15分（公式の開発者向けページ）。
  - fal.ai の FLUX 向け学習：1回 $2（1000ステップが初期値）。SDXLではない。
  - Replicate：SDXL向けの学習は検索の要約で、約 $0.6〜0.85 / 回（A100 で10分と仮定した計算を含む）。公式の料金の原文では確かめていない。
- **GPUを時間で借りる RunPod の単価**：RTX 4090 は Community Cloud $0.34/時、Secure Cloud $0.74/時（ページの構造化データ）。見える料金表の数字と食い違いがあり、ページ自体が整合していない。
- **学習に使う画像の枚数（キャラクター1人あたり）**：資料により 10〜50、15〜30、50〜100 とばらつく。公式の推奨は、取得できた範囲では無い。

- Anthropic の補足（全文）
  - 制限は組織ごと。段階は利用履歴で自動で決まる。新規や履歴が少ない組織は、表より低い「Evaluation」から始まることがある。
  - トークンバケット方式。1分あたり60回の上限は、1秒に1回として運用されることがあり、短い連続で超えうる。
  - 月の費用の上限は Start $500、Build $1,000、Scale $200,000。到達すると429（種別 `enforced_spend_limit_reached`）で、`retry-after` は付かない。再試行しても翌月まで失敗する。
  - 使用量が急に増えると「加速の制限」でも429になる。徐々に増やす必要がある。
- OpenAI の補足（取得）
  - ページに出ていたモデル名（Astra、Sol、Terra、Luna）は、実在する名前か未確認。LLMの段階の数字は、使う前にコンソールの画面で確かめる。
  - 100万トークン/分に達したら、15分ごとに50%以内の増加にとどめる、という案内がある。
  - 失敗した依頼も1分あたりの上限に数えられる。すぐ再送すると悪化する。
- Google の補足（取得）：段階は Tier 1（請求先を紐づけ）、Tier 2（$100 支払い、3日後）、Tier 3（$1,000 支払い、30日後）。

## 4. V3の設計への示唆（私の判断。設計文書への反映は別に行う）

- Nの既定は、画像生成の商用APIは 2、LLMは提供元の段階に応じて利用者が設定する。
  - 理由：fal.ai の新規が2、Runware の推奨が2〜4。これを超える既定は、新規アカウントで429や待ちを起こす。
- 上限は提供元の画面で見える値を、利用者が入れる欄にする。
  - fal.ai は画面（Concurrency ページ）で自分の上限を見られる。Anthropic は「Rate Limits API」で上限を読める（原文に記述あり）。
- 429を受けたときは `Retry-After` を優先し、無ければ指数的に待つ。fal.ai は待ち行列経由なら提供元が自動で再試行する。Runware は拒否が待ち行列に入る前なので、再試行で二重に走らない。ただし他の提供元で二重に走らないかは未調査。
- 手元のComfyUIの「1件ずつ」は、公式の実装の記述と一致している。
- 学習の時間は、手元のPCについては未検証のまま。4070 Ti で少数ステップを測る検証が要る。
