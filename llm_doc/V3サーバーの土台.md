### 1.3 利用者の名乗り方と絵の置き場（ローカル）

今はローカルで動かす（Keycloak・SeaweedFS・本番の compose は要らない）。どちらも設定で1つ選び、既定値は置かない（`server_settings.py`）。選ばなければ起動時に止まる。選んだ方式で決められなければ止め、ほかの方式で受け直すことはしない。

- 名乗り方 `V3_AUTH_MODE=dev_header`：見出し `X-V3-User` の値をそのまま利用者にする（`request_authentication.py`）。名前を書き換えれば誰にでもなれるので、ローカルと試験だけで使う。ローカルで動いていることは隠さない：起動時に警告をログに出し、全部の応答に見出し `X-V3-Auth-Mode: dev_header` を付け、`GET /health` の `auth_mode` にも出し、画面の名前の欄は「利用者（開発用）」になる。本番のイメージ（`deploy/Dockerfile`）は `V3_FORBID_DEV_HEADER=1` で、この方式では起動しない。
- 画面（`v3/web/js/api.js`）は起動時に `GET /auth/mode` で方式を読み、`dev_header` なら名前の欄の値を `X-V3-User` で送る。どの方式でも、書き換えの口には見出し `X-V3-Request: 1` を付ける（`oidc` のクッキーのときに要る。`dev_header` では見ない）。
- 試験（`tests/integration/conftest.py`）は `V3_AUTH_MODE=dev_header` と `V3_IMAGE_STORE=local` を環境変数で決めてから読み込む。
- 絵の置き場 `V3_IMAGE_STORE=local`：手元のフォルダ `V3_IMAGE_DIR`（`image_file_storage.py`）。置く前の中身は置き場の中の `staging` に一時ファイルとして少しずつ書き、置くときは名前を変えるだけ（3.3）。
- 設定 `V3_IMAGE_STORE` で選ぶ（既定値は無い）。`local`（手元のフォルダ `V3_IMAGE_DIR`。開発用）か `s3`（S3互換）。選んだ置き場に届かなければ止める。もう一方を代わりに使うことはしない。口と作業者は起動時に置き場を確かめ（`image_store().check()`）、届かなければ起動しない。
- `V3_IMAGE_DIR` が空のまま `local` を選ぶと止まる（前は空の文字列が今いるフォルダの意味になっていた）。
- キーは手元のフォルダと同じ `<sha256 の先頭2文字>/<sha256>`。中身の sha256 が名前なので、同じ絵は1つだけ置かれ、置いた物は書き換えない。
- 書き出したファイル（PNG・PDF・PSD）は、今も手元のフォルダ（`V3_EXPORT_DIR`）。本番では口と作業者が同じ volume（`exports`）を使う。サーバーを2台にするときは、ここも S3 に移す必要がある（まだ）。

#### 1.4.1 ログイン（Keycloak）

2026-10-08 に作った。試作 p54 で比べた Keycloak と Ory のうち、**Keycloak 26.8.0** にした。

- 選んだ理由：コンテナ1つで、ログインの画面・利用者の管理の画面・パスワードの再設定・招待（管理者が利用者を作る）まで揃う。Ory は Kratos・Hydra・ログインの画面の3つを組み、クライアントの登録も別に要る（p54：設定 4ファイル100行）。Ory の方が軽い（起動11秒・151MiB、Keycloak は68秒・650MiB）が、1つの作業場で動かす規模では起動の遅さとメモリより、組む物の少なさを取った。どちらも Apache-2.0。
- Keycloak の保存先は、正本と同じ PostgreSQL のデータベース `keycloak`。控え（1.4.4）を1回で取るため。
- 方式は設定 `V3_AUTH_MODE` で1つ選ぶ（既定値は無い）。選んだ方式で利用者を決められなければ 401。別の方式で受け直すことはしない（`request_authentication.py`）。

| 方式 | 使う所 | 中身 |
|---|---|---|
| `oidc` | 本番 | 画面は `/auth/login` → Keycloak → `/auth/callback`（認可コード＋PKCE。手順は Authlib 1.8.0）。利用者はクッキーのセッション（Starlette の `SessionMiddleware`、署名した `v3_session`、SameSite=Lax、https なら Secure）。スクリプトは `Authorization: Bearer <Keycloak のアクセストークン>`（PyJWT で署名・発行元・宛先 `v3-server`・期限を確かめる。p54 と同じ確かめ方） |
| `dev_header` | 開発と試験だけ | `X-V3-User` の値をそのまま利用者にする。起動時に警告を出し、全部の応答に見出し `X-V3-Auth-Mode: dev_header` を付け、`GET /health` の `auth_mode` にも出す。画面の名前の欄は「利用者（開発用）」になる。本番のイメージ（`deploy/Dockerfile`）は `V3_FORBID_DEV_HEADER=1` で、この方式では起動しない（確かめた） |

- 利用者の ID は Keycloak の `sub`。OpenFGA では `user:<sub>`。`GET /auth/me` が ID・名前・メール・OpenFGA の user を返す。最初の管理者は、その ID を `admin_command_line grant-admin <ID>` に渡す。名前（`preferred_username`）は変えられるので、権限には使わない。
- セッションの期限は `V3_SESSION_MAX_AGE_SECONDS`。ログインした時から数え、使い続けても延びない。
- ログアウト：`GET /auth/logout` でセッションを消し、Keycloak のログアウト（`id_token_hint` 付き）へ送る。
- よそのページからの書き換えを断る：クッキーで GET 以外の口を呼ぶときは、見出し `X-V3-Request: 1` が要る（無ければ 403）。画面（`v3/web/js/api.js`）は常に付ける。Bearer のときは要らない。
- Keycloak の設定：realm `v3` とクライアント `v3-server` は `deploy/keycloak/realm-v3.json` を初回の起動で読み込む（既にあれば読まない）。自分での登録は切ってある（管理者が利用者を作る）。アクセストークンの宛先に `v3-server` を入れる設定を足した（Bearer の確かめで宛先を見るため）。

#### 1.4.2 S3互換の置き場（SeaweedFS）

#### 1.4.4 控えと戻し

```
deploy/backup.sh  .env.prod <project 名>                 # 動かしたままでよい。<V3_BACKUP_HOST_DIR>/<UTC の時刻>/ に置く
deploy/restore.sh .env.prod <新しい project 名> <時刻>   # 空の新しい環境へ戻す（volume があれば止める）
uv run python deploy/check_production_stack.py .env.prod <project 名> verify|fingerprint <ファイル>
```

- PostgreSQL は `pg_basebackup`（`-Ft -z -X stream`）で、サーバー全部（正本・OpenFGA の役・Keycloak の利用者・Temporal）を同じ時点で取る。データベースごとに `pg_dump` すると時点がずれ、作品と役が食い違うことがあるため。
- 絵は DB の後に rclone で写す。絵は名前が中身の sha256 で、書き換えず、消す仕組みも無いので、DB の控えが指す絵は必ず絵の控えに入る。絵を消す仕組みを足すときは、控えの保持期間より古い物だけ消すようにする（この順が崩れるため）。
- 戻すとき：`.env.prod` は控えを取った元と同じ値にする（DB の利用者のパスワードと Keycloak のクライアントの秘密は控えの中の値が使われる。Keycloak の戻り先の住所も控えの中にある）。`.env.prod` は控えに入れないので、別の安全な所に置く。
- 書き出したファイルは控えに入れない（流し直せば作れる）。
- 控えを取る時期・何世代残すか・別の場所へ送るかは、まだ決めていない。

2026-10-08 に、次の手順で本当に戻して確かめた（project `v3a4proda` → `v3a4prodb`、どちらも同じ住所 `https://localhost:18443`）。

1. 元の環境で `check_production_stack.py seed`：Keycloak に3人作り、ブラウザと同じ手順（Caddy の TLS 越し、Caddy の内部の CA の根の証明書で確かめる）でログインし、作品・ページ・絵3枚・viewer の招待・書き出し（PNG）を作った。
2. 控えの前後で `fingerprint`（データベース `v3`・`openfga`・`keycloak` の全部の表 140 の行数と中身のハッシュ、置き場の全部の物の sha256）を取り、前後で同じだった。
3. `backup.sh`：PostgreSQL 9.5MB、絵 9。
4. 元の環境を止め、`restore.sh` で新しい project に戻した。PostgreSQL は「consistent recovery state reached」で起動した。rclone の `check` で絵 9 が一致した。
5. 戻した先の `fingerprint` を元と比べた：`v3`（33表）・`openfga`（6表）・絵 9 はすべて同じ。`keycloak` は 101表のうち `jgroups_ping`（同じ組の Keycloak を見つけるための、起動した物の住所）と `server_config` の2つだけが違った。どちらも Keycloak が起動のたびに書き直す行。
6. 戻した先で `verify`：作者でログインでき、作品と絵3枚が読め、絵の中身の sha256 が合った。viewer は読め、作品に居ない人は 403（OpenFGA の役が戻っている）。`/health/ready` が通った。
7. 戻した先で、もう一度 `seed` を流し、8項目すべて通った（新しいログイン・書き出しが Temporal と作業者を通る）。

## 3. 正本と操作の窓口

- 正本を変えるのは `POST /works/{id}/ops` と取り消し（`POST /works/{id}/events/{event_id}/undo`）だけ。どちらも操作の窓口を通る。
- 1回の操作の流れ
  1. 作品の行を `FOR UPDATE` で取る。作品ごとに書き込みは1本になる（`V3ハーネス設計.md` 9.3）
  2. 権限を確かめる。AIは頼んだ人の権限で確かめる
  3. ロックを確かめる
  4. 正本を変え、出来事を1件追記する。出来事には取り消すときに流す操作も入れる。AIの変更が人の手の印に当たって判断待ちに置いた項目も出来事（`held_changes`）に残し、返事で返す（3.2）。変えた行と項目（前の値と後の値）も出来事（`field_changes`）に残す（3.0）
  5. 権限の組（OpenFGA）を書いてから確定する。確定に失敗したら書いた組を戻す
- 操作を足すときは `operations/` に操作の型を1つ書き、`operations/all_operation_types.py` の `Op` の一覧に加えるだけ。窓口（`operations/operation_submit_and_undo.py`）と取り消しは触らない。

| 操作 | 要る権限 | 取り消し |
|---|---|---|
| 作品の設定（題・読む向き・文字の向き・媒体・判型・ページ数） | 作者 | 元の値に戻す |
| 人を招く・外す | 作者 | 逆にする |
| 送ってよい先（APIのつなぎ先）を足す・外す | 作者 | 逆にする |
| 閾値を置く・変える・外す | 作者 | 元の値に戻す |
| 指摘への反応（直した・見送った・指摘が違う） | 見られる人 | できない（記録なので、違えば足し直す） |
| 巻・話・ページを足す | 作者 | 抜く |
| 話を変える（題・番号・締切） | 作者 | 元の値に戻す |
| ページをアシスタントに割り当てる・外す | 作者 | 逆にする |
| コマを足す | そのページを描ける人 | 抜く |
| コマを変える（読む順・枠・役割・中身・使う絵・人の確定印・人の手の印） | そのページを描ける人 | 元の値に戻す |
| ページの段の割りを変える | そのページを描ける人 | 元の値に戻す |
| 巻・話・ページ・コマを抜く・戻す | 作者（コマはそのページを描ける人） | 逆にする |
| ネームの案を出す | 見られる人 | 案を「使わない」にする |
| ネームの案を「使わない」・未決に戻す | 見られる人 | 元の状態に戻す |
| ネームの案を採用する | 作者 | 採用する前のページとコマに戻し、作ったページとコマを抜く |
| 絵を登録する | ページの絵はそのページを描ける人、ページに属さない絵は作者 | できない（絵は消さない） |
| コマを分ける・合わせる・ばらばらに割る・図形のコマ・コマの型を当てる | そのページを描ける人 | 1回で前の行に戻す（`restore_rows`） |
| コマの型を残す | そのページを描ける人 | 抜く |
| トーン・図形を置く・変える・動かさない・仕上げをまとめて戻す | そのページを描ける人（動かさないは人だけ） | 元の値に戻す |
| ペンの線を足す・変える・抜く・線の消しゴム・画素の消しゴム・線の控えの絵 | そのページを描ける人。人だけ | 1回で前の行に戻す |
| 赤入れを付ける・直す・依頼を残す | 赤入れを付けられる人（can_comment） | 元の値に戻す |
| 企画・設定資料を変える・設定資料の案を採る | 作者 | 元の値に戻す |
| 置き換え | 1ページならそのページを描ける人、いくつものページなら作者 | 1回で前の行に戻す |
| 直した PSD を戻す | そのページを描ける人。人だけ | 1回で前の行に戻し、作った判断待ちは取り下げ |
| 今のアプリのプロジェクトを取り込む（`import_current_app_project`） | 作者。人だけ | 1回で、作ったページ・コマ・層・文字・AIの設定を抜く（絵と報告は残す） |
| 訳文を置く・変える・抜く（`set_text_translation`・`set_text_translation_removed`） | 翻訳できる人（can_translate：作者・翻訳者） | 元の値に戻す・足した訳文を抜く |
| 確認の状態を変える（`set_review_status`） | 移り方で決まる（3.5）。人だけ | 前の状態へ戻す記録を足す |
| ページを並べ替える（`reorder_pages`） | 作者。人だけ | 前の番号に戻す |
| 見開きにする（`add_spread`）・解く・戻す（`set_removed` の `spread`） | 作者。人だけ | 逆にする |
| 見開きの絵を置く・替える（`update_spread`） | 前のページを描ける人。人だけ | 元の値に戻す |
| ページの種類・色の種類・解像度・ノンブルの出し方（`update_page`） | そのページを描ける人。人だけ | 元の値に戻す |

- どの操作でも、AIの変更が人の手の印の付いた項目に当たると、断らずにその項目を判断待ちに置き、印の無い項目は当てる（3.2）。どの操作が `V3細部の決めごと.md` 10.1・10.4 のどの行を受けるかは `V3人とAIの受け渡し.md` 6章。
- 消さずに「抜いた」印を付けるので、取り消しの取り消しでやり直しになる。同じ出来事は2回取り消せない。
- 作品を作ったときの出来事（`create_work`）と、ロックの出来事（`lock_acquired`・`lock_released`・`lock_preempted`）も出来事の列に入る。どれも取り消せない。
- ネームの形（ページ・段・コマ・写す範囲・角度・人物・吹き出し・擬音）は `name_structure/name_draft_schema.py` に置いた（試作 p27 の出力の形）。ページとコマの行と、この形の間は `operations/name_draft_conversion.py` で変換する。検査とコマ割りの計算は、この形だけを見て、誰が作ったかは見ない。

### 3.0 取り消しが後の変更を上書きしない（点検1 8-1・点検5 4-1。2026-10-08）

- 操作の窓口が、操作の間に変わった行と項目を SQLAlchemy の変更の記録から集め、出来事の `field_changes` に残す（`operations/field_change_record.py`）。操作ごとに書き足す物は無い。
- 出来事 E を取り消すとき、取り消しが戻す項目ごとに、今の値が「E の後の値」のままかを比べる。違えば、その項目を E より後に変えた出来事を挙げ、取り消しは当てない。返事は 409（`code: undo_conflict`、`conflicts` に表・行・項目・後で変えた出来事、`undo_conflict_id`）。止めた取り消しは `undo_conflicts` の表に残し、`GET /works/{id}/undo-conflicts` で読める。
- E が足した行を取り消しで抜くときは、後の出来事を通して値が変わったままの項目がその行にあれば止める（変えて戻した項目は数えない）。
- 別の項目を後で変えていても、取り消しは通る。人の手の印は、E が付けた・外した分だけを戻し、後の出来事が付けた印は残す。線の版（`stroke_revision`）は数え上げるだけなので比べない。
- 記録を始める前の出来事（`field_changes` が空）は、ぶつかるかを確かめられないので取り消さない（`not_undoable`）。
- `V3細部の決めごと.md` 16章は「2人の保存がぶつかったときは、後から保存した側を別の版にする。どちらも消さない」と決めている。ぶつかった取り消しは、どちらも消さない（後の人の値は正本に残り、取り消そうとした値は E の `field_changes` と `undo_conflicts` に残る）。「別の版にする」は、版（名前を付けた版・枝分かれ）の仕組みが無いので作っていない。版を持つには正本の形を作り直す必要があり、この直しでは入れていない（点検1 8-2・8-3）。ぶつかった取り消しを人がどう片付けるか（相手の変更を取り消してから取り消す・手で直す）の画面も無い。

### 3.1 ネームの案

- 作り手は3つ：AIが作った（`ai`）・人が別に作った（`human`）・外のネームを取り込んだ（`imported`）。どれも同じ形で、採用すると同じページとコマの行に入る。
- 作り手は偽れない。AIの操作はAIの案だけ、人の操作は人の案か取り込みの案だけを出せる。
- 案そのものは採用しても消さずに残す。採用した案の状態は、採用を取り消すまで変えられない。
- 見る口：`GET /works/{id}/episodes/{episode_id}/name-proposals`（案の一覧）、`.../name-draft`（今のページとコマをネームの形にして返す）。

### 3.2 人の手の印（`V3細部の決めごと.md` 10.2）

- ページとコマを変える操作は、必ず `operations/human_hand_guard.py` を通す。
- 人が変えた項目には、項目ごとに人の手の印を付ける。
- AIは、人の手の印の付いた項目と、人の確定印の付いたコマを書かない。AIの変更が当たると、断らずにその項目を判断待ちに置き、印の無い項目はそのまま当てる。印・確定印のある行をAIが抜く・戻すときも判断待ちに置く。どの操作も `human_hand_guard.py` の1か所を通るので、操作ごとの違いは無い（2026-10-08 に揃えた。前は前からある操作だけ 409 で断っていた）。
- 判断待ちに置いた項目（判断待ちの id・表・行・項目）は、出来事の `held_changes` に残り（移行 0007）、`POST /works/{id}/ops`・取り消しの口の返事の `held_changes` と、`GET /works/{id}/events` で見える。AIの操作を流す側（順番待ちの作業者など）は、返った出来事の `held_changes` で分かる。
- 人は `GET /works/{id}/held-changes` で見て、`resolve_held_change` で採る（accept）・採らない（reject）・戻す（reopen）を選ぶ。判断待ちを置いた操作を取り消すと、まだ決めていない判断待ちは withdrawn になり、やり直すと開き直す（窓口が取り消しの操作を `undo_with_held_changes` で包む）。
- 人の手の印を外せるのは人だけ（`human_hand_fields` を明示して渡す）。
- 人が案を採用したときは上書きする。人の案・取り込みの案なら書いた項目に印を付け、AIの案なら印を外す。
- AIが案を採用したとき・人がAIの案を採用したときは、人の手の所と確定印のコマは書かず、判断待ちに置いて出来事に残す。

### 3.3 絵のファイル

- 生成した絵・人が描いた絵・外から持ち込んだ絵を、同じ表（`image_files`）と同じ操作（絵を登録する）で持つ。違うのは出どころの印だけ。
- 出どころは偽れない。AIが登録できるのは生成した絵だけ（依頼の ID が要る）。人は描いた絵と持ち込んだ絵（持ち込みは元を書く）。
- ファイルの中身は置き場に、中身の sha256 を名前にして置く。同じ絵は1つだけ置かれる。今の置き場はサーバーの手元のフォルダ（`.env` の `V3_IMAGE_DIR`）だけ。無ければ絵を扱う口は止まる。
- 受け付ける形式は PNG・JPEG・WEBP・TIFF。
- アップロード（2026-10-08。点検5 3-1・3-2）
  - 権限とロックを、ファイルを書く・判定の記録を確定する前に確かめる。確かめる中身は登録の操作と同じ（`register_image_scope` と `check_scope`。見るだけの人は 403 で、ファイルも記録も残らない）。PSD を戻す口も、当てる操作（`ApplyPsdImport`）の権限とロックを先に確かめる。
  - ファイルは丸ごとメモリに読まず、置き場の中の `staging/` に少しずつ写してから確かめ、置くときは名前を変えるだけ（`image_file_storage.staged_file`）。
  - 要求の本体の上限 `V3_REQUEST_MAX_BYTES`：全部の口にかける中間層（`http_routes/request_size_limit.py`）。Content-Length が超えていれば読まずに 413。無い・偽った要求も読んだ量で止める。
  - 画素数の上限 `V3_IMAGE_MAX_PIXELS`：外から入る絵（アップロード・生成した絵・PSD の層）は、画素を展開する前に幅×高さを比べる（`image_intake.check_pixel_count`）。Pillow の `DecompressionBombWarning` も止めとして扱う。上限を Pillow の `Image.MAX_IMAGE_PIXELS`（89,478,485）より大きくすると断る（後で絵を開く所で警告になるため）。
  - PSD は紙の画素数・層の数（`V3_PSD_MAX_LAYERS`。グループも数える）・層ごとの画素数を、層を展開する前に比べる（`read_psd`）。層の絵の判定の記録は、当てる出来事と同じ確定に入れる。
  - ペンの口（`pen_stroke_routes.py`）の絵のアップロードは、ほかの作業で直している最中のため触っていない。上限（本体・画素数）は入口の共通の所でかかる。権限を先に確かめる順と、丸ごと読む所はそのまま。
- 口：`POST /works/{id}/images`（人が描いた絵・持ち込んだ絵を受け取る）、`GET /works/{id}/images`、`GET /works/{id}/images/{image_id}/file`。生成した絵は、順番待ちの作業者が頼んだ人の権限で同じ操作を使って登録する（7章）。
- コマに使う絵を選ぶのはコマを変える操作の `image_id`。人が選ぶと人の手の印が付き、AIが替えようとすると判断待ちになる。
- 画像生成（文から絵・絵から作り直す・似た別案・囲んで直す・描き足す・指示で直す）は、処理の一覧（`generation_queue/image_process_registry.py`）から引数・入力欄・ComfyUI の手順を作る。できた絵は候補として登録され、採用・取り消し・却下・比べる・版を見るができる。口・下ごしらえ・画面は `V3画像生成の機能と画面.md`。

### 3.3.1 ペンの線（移行 0010。2026-10-08）

- 点は `[x_mm, y_mm, 筆圧, ms]`。筆圧は、機器が返したときだけ 0〜1 の数、返さないときは null（作った値を入れない。点検3 2.1）。1本の中で null と数を混ぜると断る。線ごとに描いた機器 `pointer_type`（`pen`・`mouse`・`touch`。古い線は null）を持ち、`mouse` で筆圧のある線は断る。分けた線・消しゴムで切った線も、元の機器と筆圧（null のまま）を受け継ぐ（`hand_tools/vector_strokes.py`）
- 線の id は画面で作ってよい（32桁の16進。`add_pen_strokes` の `strokes[].id`）。同じ id がすでにあれば断る。画面が保存を待たずに取り消しの記録に載せるため
- 線ごとに外接の箱（`box_x0_mm` など。点の範囲 ± 太さの半分）を持つ。箱は SQLAlchemy の `before_insert`・`before_update` の1か所で点から計算する（取り消しで行を戻すときも同じ所を通る）。PostgreSQL の GiST の索引（`box(point, point)` の式）で、線の消しゴムは通り道の箱に重なる線だけを読む。交わる所まで消すときも、触れた線の箱に重なる線だけを読み、区間どうしの交わりは shapely の STRtree で探す（shapely 2.1 以上、BSD-3）
- 口
  - `GET /works/{id}/panels/{panel_id}/layers`：コマの行（id・ページ・順・絵・置き場・抜いた印）と層の一覧。画面がコマを替えるときに読む（作品全体は読まない）
  - `GET /works/{id}/layers/{layer_id}/pen-strokes?after=-1&limit=500&points=true`：抜いていない線を `stack_order` の順に区切って返す（`limit` は 2000 まで）。`next_after` が null でなければ続きがある。`points=false` なら点を省く（画面の線とサーバーの線が同じか比べるとき）。`stroke_revision`・`image_stroke_revision` も返す
  - `GET /works/{id}` はペンの線を返さない（線の多い作品で重くなるため）
- 3,000本の線の層で、線の消しゴム1回：線ごと 120ms・交わる所まで 766ms・触れた所 314ms（このコンテナ、1回ずつ）。索引が線の数がもっと多いときに効くかは未検証

### 3.4 ネームの検査

- `POST /works/{id}/episodes/{episode_id}/name-checks` で回す。`proposal_id` を渡すと採用する前の案を、渡さなければ今のページとコマを検査する。どちらも同じ検査にかかる。
- 閾値は作品の閾値の表から、検査の鍵の行だけを読む。値の形は `{"value": 数}`。検証の状態が `rejected` の行は使わない。`unverified` の行は使い、結果に状態を添える（`V3ハーネス設計.md` 7章）。
- 閾値の無い検査は値だけを返し、合否を出さない（「閾値未設定」）。枠・人物の位置・吹き出しの位置が無いと計算できない検査は「データなし」。
- 結果は回すたびに1行足す（`name_check_runs`。使った閾値も残す）。作品データではないので操作の窓口を通さない。`GET` で一覧を見る。鍵と意味の一覧は `GET /name-checks/threshold-keys`。

### 3.5 確認の状態と進み具合（2026-10-08）

- ページと作品が状態を持つ：下書き（draft）・確認待ち（in_review）・承認（approved）・直しが要る（needs_changes）。行（`review_states`）の無いものは下書き。変えるたびに記録（`review_records`：前と後・コメント・誰が・何の取り消しか）を1行足す。操作は `set_review_status`（`operations/review_operations.py`）。AIは出せない
- 移り方と出せる人

| 移り方 | 出せる人 |
|---|---|
| 下書き → 確認待ち、直しが要る → 確認待ち、確認待ち → 下書き（引っ込める） | ページはそのページを描ける人、作品は作者 |
| 確認待ち → 承認、確認待ち → 直しが要る（コメントが要る）、承認 → 下書き（開け直す） | 承認できる人（`can_approve`：作者・編集者） |

- 上のほかの移り方（下書きから承認へ飛ぶなど）は止める。取り消しは前の状態へ戻す記録を足し、戻す権限は元の移り方と同じ（アシスタントは承認を取り消せない）
- 口：`GET /works/{id}/review-records`（`target_id` で絞れる）、`GET /works/{id}/progress`（`review_progress.py`）
- 進み具合は話ごとに、状態ごとのページの数・確認待ちのページ・直しが要るページ・締切・締切を過ぎて承認していないページがあるか、を返す
- 締切の見込み（`V3細部の決めごと.md` 19章。未検証）：この作品で1枚にかかった時間 =（今 − 作品を作った時）÷ 作品の承認したページの数。話の承認していないページを番号の順に1枚ずつ足して終わる時を出し、締切より後になるページを挙げる。承認したページが無ければ見込みは出さず理由を返す。待ち行列の時間はまだ入れていない。当たるかは作ってみるまで分からない

## 6. 送り先の制限

- 手元（`location=local`）は外へ出ないので、どの作品からも送ってよい。
- 「手元」と言えるもの（`allowed_destinations.proves_local`。2026-10-08、点検5 5-2）：送り先へ直接送る送り手（`comfyui`・`detector`）で、`endpoint` の住所がこのサーバーと同じ機械（127.0.0.0/8・::1 の数字の住所か `localhost`）を指すもの。
  - `litellm` は手元と言えない。LiteLLM 自体は手元でも、その先のモデルが外の API かは LiteLLM の設定次第で、サーバーからは見えない。
  - 社内の別の機械（10.x・192.168.x など）も手元と言えない。その住所が外への中継でないかを確かめられない。`api` として登録し、作品ごとに送ってよい先へ載せる。
  - `localhost` の名前がどこを指すか（hosts の設定）は確かめていない（未検証）。数字の住所なら確か。
  - 言えないものを `local` で登録・変更しようとすると 422。前から `local` で登録してある言えない物は、`api` と同じに扱う（送ってよい先に載せるまで送らない。口と画面にも `api` と出す）。
- API（`location=api`）は、作品の送ってよい先に載っているものだけ。新しい作品では空なので、既定は「手元だけ」（`V3ハーネス設計.md` 17章の6）。
- 確かめるのは2回。頼んだとき（送れない先なら403）と、送る直前（待っている間に外されたら送らず、止まった印を付ける）。
- 別の先へは自動で回さない（方針7）。

## 7. 順番待ち

- 1件の依頼は Temporal の流れ1つ。流れは制御の待ち行列（`v3-control`）で動き、送信はつなぎ先ごとの待ち行列（`v3-service-{id}`）で動く。
- 「1件ずつ」は作業者の同時実行数を1に、「同時にN件まで」はNにする（`V3細部の決めごと.md` 4.2）。
- 休ませたつなぎ先は作業者を止める。頼んだものは待ち行列に残り、戻すと順に送る。作業者はつなぎ先の表を3秒ごとに読み直す。
- 人が画面で頼んだものを、AIが工程を進めるための依頼より先に送る（同 4.4）。Temporal の優先順位（`priority_key`、人1・AI3）を使う。
- 優先順位が同じ依頼の中では、作品ごとに順に回す（`V3ハーネス設計.md` 2.4の29）。Temporal の公平さの鍵（`fairness_key`）に作品の ID を入れる。サーバー側で `matching.enableFairness` を入れていないと鍵は無視されるので、compose で入れてある（試作 p57）。
- 送る前に、作品の送ってよい先と、つなぎ先の月の予算（呼び出しの記録の費用の合計）を確かめる。予算は、つなぎ先の行を `FOR UPDATE` で取ってから数え、この回の費用を取り置いて（呼び出しの記録 `sending` に費用を入れて）確定する。同時に送れる先でも、並んだ依頼が上限を超えない。送って失敗したら取り置きを外す。
- 作業者が途中で落ちても二重に送らない・二重に登録しない（2026-10-08。点検5 4-2。`generation_queue/service_call_activity.py`）
  1. 送る前に、この回の鍵（`idempotency_key`。依頼・ワークフローの回・活動の呼び出し・回数）と取り置きを持った記録（`sending`）を確定する。鍵は送り先には渡していない（受け付ける先があるかは未検証）
  2. 受け取ったら、絵を置き場に置き、答え（`result`）と入口の判定の記録を1回で確定する（`received`）
  3. 絵の登録・答えの取り込み・記録（`ok`）・依頼の終わり（`done`）を1回で確定する（操作の窓口の `commit=False`）
  - Temporal がやり直したとき、前の回の答え（`received`）があれば送らずにそれを登録する。3 の途中で落ちても何も残らないので、次の回は同じ答えで1回だけ登録する。
  - 送った後、答えを残す前に落ちたときは、前の回の記録が `sending` のまま残る。次の回はそれを `unknown`（送ったか分からない。取り置きは残す）にして、もう一度送る。時間切れ・通信の失敗と同じ扱い（`V3細部の決めごと.md` 4.5）。この場合は二重に送りうる。
  - 送っている間に人が取り消したときも `unknown`（取り置きを残す）にする。生成中に止めたときに課金されるかは提供元による（未確認）。
  - 答えが崩れていた・入口で止めた・置き場が無いときは `failed`（費用はかかっているので取り置きは残す）。
- 頼んだ順を守るため、依頼を受ける口（`POST /works/{id}/jobs` など。中は `job_start_and_control.enqueue`）は、送信がつなぎ先の待ち行列に入ってから返す。流れを始めるのと、流れの更新 `until_queued`（送信を待ち行列に入れたら返る）を1回で頼む（Temporal の update-with-start）。始めただけで返すと、続けて頼んだ依頼が待ち行列に入る順が頼んだ順と入れ替わった（下の8章）。
- `QUEUE_ENTRY_WAIT`（30秒、`queue_names_and_priority.py`）待っても待ち行列に入らなければ（制御の作業者が動いていない）、流れを終わらせ、依頼を `stopped`（失敗の種類 `queue_not_running`）にし、口は 503 を返す。

失敗したとき（`V3細部の決めごと.md` 4.5）

| 失敗 | 依頼の状態 | 扱い |
|---|---|---|
| 回数・同時実行の制限 | `waiting_limit` | 提供元が返した時間（無ければ30秒）待って、同じ先へ送り直す。送り直しの回数に数えない |
| 時間切れ・通信の失敗 | `running` のまま送り直し、超えたら `stopped` | 処理ごとの `resend_limit` 回まで送り直す |
| 内容で断られた | `stopped` | 送り直さない |
| 返ってきた形が崩れている | `stopped` | 使わない |
| 予算の上限 | `waiting_budget` | 人が上限を上げて「続ける」（`/resume`）を押すまで待つ |
| 送ってよい先から外された | `stopped` | 送らない |
| 待ち行列に入れられなかった（制御の作業者が動いていない） | `stopped`（`queue_not_running`） | 口は 503 を返す。「もう一度」で頼み直せる |

- 止まったものは「もう一度」（`/retry`）で、いまの処理ごとの送り先へ同じ中身で頼み直す。
- 取り消す（`/cancel`）と、送っている途中でも止めて `cancelled` にする。
- 呼び出しの記録には、送った・送らなかったの両方を残す（呼び先・モデル・設定・seed・トークン数・費用・時間・失敗の種類・鍵・受け取った答え）。状態は `sending`・`received`・`ok`・`unknown`・`failed`・`blocked`。予算に数えるのは前の4つ。費用はつなぎ先と処理の組ごとに人が入れた1回の単価。

ComfyUI への送信（`service_senders/comfyui_sender.py`。試作 p56 で本物の ComfyUI 0.39.2 に送って確かめた形）

- 処理ごとの送り先に手順（API 形式）を持たせ、依頼の `overrides`（ノード番号 → 入力名 → 値）で値を差し替えて `/prompt` に送る。`/history` で終わりを待ち、`/view` で絵を受け取る。
- 受け取った絵は置き場に置き、依頼の `register`（絵の役目は必須、ページ・コマは省ける）で登録する。登録の役目が無い依頼は送らずに止める。登録を断られたら依頼は止まる。
- 処理ごとの送り先に、待ちの上限（秒、`comfy_wait_seconds`）と、送る前に選べる値を ComfyUI の一覧で確かめるかの切り替え（`comfy_check_choices`）を持つ。

| ComfyUI の返事 | 失敗の種類 |
|---|---|
| `/prompt` の 429 | 回数・同時実行の制限（`Retry-After` を使う） |
| `/prompt` の 5xx | 通信の失敗 |
| `/prompt` のほかの 4xx（手順を確かめて断った） | 内容で断られた。`error.type` と `node_errors` の要点を詳細の先頭に出す |
| `/history` の 429・5xx | 制限・通信の失敗 |
| `/history` のほかの 4xx、辞書でない本体 | 返ってきた形が崩れている |
| 実行時の失敗 | 内容で断られた（詳細は `exception_message`） |
| 外から止められた | 止められた（`interrupted`） |
| 待ちにも実行中にも履歴にも無い、待ちの上限を超えた | 通信の失敗 |

- 取り消すと、待ちの物は `/queue` から消し、自分の依頼が実行中なら `/interrupt` で止める。

検出器への送信（`service_senders/detector_sender.py`）

- 依頼の `endpoint` で検出器の口を選び、`images` に絵の sha256 を入れる。絵は置き場から読んで送る。閾値などは `form` で渡す（省いた項目は検出器の側で imgutils の既定に任せる）。
