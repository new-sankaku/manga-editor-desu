# V3 の AIハーネスの実装（2026-10-08）

`v3/server/src/v3server/harness/` に置いた工程の進行役と作業の流れ、それを見て動かす画面 `v3/web/harness/` の文書。
設計は `V3ハーネス設計.md`、細部は `V3細部の決めごと.md`。ここには、作ったもの・確かめたこと・まだ作っていないものを書きます。

## 1. 作ったもの

### 1.1 流れ（Temporal）
- **StageWorkflow**（`stage_workflow.py`）が1つの工程の実行（S0〜S7 のどれか1つ）を進めます。作業を切り出し（`prepare_stage`）、
  同時に回す数の上限まで子の作業を起こし、全部が終わったら工程の検査（`stage_check`）をして、人の承認を待ちます。
  承認されると次の工程の実行を作ります（`advance_stage`。S7 の次はありません）。
- **WorkUnitWorkflow**（`unit_workflow.py`）が作業1つの流れです。段は「切り出し → 文脈 → 生成 → 検査 → 直させる → 評価 → 人の判断 → 確定」。
  - 検査で落ちた候補のうち、落ちた所が囲める物（文字・顔）は「直させる」段で囲んで直し、直した候補だけを検査し直します。
    回数は作業の上限 `max_fix_rounds` までです。上限に達したか直せない物は、文脈へ戻って全部を作り直します。このとき出来事 `fix_fallback` を残します。
  - 評価で選べない・割れたとき（文脈へ戻る）と、却下（人の判断 → 文脈へ戻る）の線もあります。
- **どの工程も作業を切り出します**（`harness_states.UNIT_KIND_OF_STAGE`）。人が決める所は、作業の中の「人の判断」の段にしています。

  | 工程 | 作業の種類（ファイル） | AI・プログラムがすること | 人だけがすること |
  |---|---|---|---|
  | S0 企画 | `plan_interview`（`plan_interview_steps.py`） | LLM が人への質問か企画の案を作る。必須項目がそろうかを検査 | 質問に答える（review の `answer`）・案を採る |
  | S1 構成 | `structure`（`structure_steps.py`） | LLM が1話のページ配分・見せ場・伏線を作る。ページの数と番号を検査、観点ごとの判定は指摘だけ | 採る（`EpisodeOutline` を書く） |
  | S2 設定資料 | `settings_sheet`（`settings_sheet_steps.py`） | LLM が人物と場所の文章と絵を作る言葉を作る。主要な人物の見分けを指摘 | 採る（既にある名前は足さない）。参照の絵を置く |
  | S3 ネーム | `name_draft` | 前からのまま | 採る |
  | S4 作画 | `panel_drawing` | 生成・検査・直させる・評価役 | 完成条件に `human_approve` を入れたときだけ採る |
  | S5 仕上げ | `page_finishing`（`page_finishing_steps.py`） | 人が置いた吹き出し・文字を写して検査するだけ（ネームの検査・顔の隠れ・読む順） | 吹き出し・文字・擬音を置く |
  | S6 総合 | `overall_review`（`overall_review_steps.py`） | ページを描いて黒の量・白さを測り、VLM が要約と構成との食い違いを書く | 見て完成とする |
  | S7 書き出し | `export`（`export_steps.py`） | 決めた形で書き出し、入稿前の確かめを指摘にする | 見て採る（提出。外へは送らない） |

  - 人が採るまで終わらない工程は `HUMAN_APPROVE_STAGES`（S0・S1・S2・S3・S6・S7）です。完成条件に `human_approve` を必ず足します。
  - S5〜S7 の指摘では候補を落としません。候補は今の原稿を写した物・測った物なので、落としても同じ物を作り直すだけになるためです。
  - S0〜S2・S5〜S7 が共に使う部品は `stage_steps_common.py` にあります。LLM の問いは `llm_questions/` の
    `plan_interview_question.py`・`structure_question.py`・`settings_sheet_question.py`・`overall_review_question.py` で、どれも LiteLLM を通します。
  - review の `answer` は、モジュールで `TAKES_ANSWERS = True` とした作業（今は `plan_interview` だけ）にしか使えません。ほかの作業では口が 422 で断ります。
- 判断待ち・止めた・止まった・決めるまで進めない（`WAITING_HUMAN`）の作業は、同時に回す数に数えません。
  人を待つ作業が上限を埋めて、ほかの作業が進まなくなるのを避けるためです。
  作業がこの状態に入るときと出るときに、親へ `unit_waiting` の Signal を送ります。
- 止める操作は3つです。
  - 段の切れ目で止める
  - 今すぐ止める：ComfyUI の実行を `prompt_id` 付きで止めます。再開すると同じ段からやり直します
  - 取り消す：半端な候補は却下にします
- そのほかの操作は次のとおりです。
  - 上限を変える
  - 人の判断：採用、理由をつけた却下、人が直した絵から続ける（人の手の範囲を守る処理で作ります）
    - **却下は止まるだけです**（決めごと 5.3。2026-10-08 に直しました。前はすぐ作り直していました）。今の回の候補を却下にして
      「止まった」になり、人が再開を押すと、却下の理由を次の回の問いに入れて作り直します。止まっている間に上限を変えても続きません。
      すぐ作り直すのは、上限の `redo_on_reject` を入れたときだけです（決めごと 9章の4。既定は入れません）。画面のボタンも
      「却下して止める」と「却下して作り直す」をこれで切り替えます。
- 上流（コマの中身・設定資料など）が変わると「古い」の印を付けます（`upstream_watch.py`）。自動では作り直さず、人が頼んだときだけ作り直します。
  印の付いた作業がまだ動いているときは、段の切れ目で止めます。
- **時間の上限（`budget_seconds`）には、段を動かした秒だけを数えます。** 送り先の順番待ち（段の依頼がどれも動いていない間）は
  数えず、別の上限 `wait_seconds`（1つの段の中の待ちの合計）で持ちます（`queue_calls.WaitClock`）。待ちの上限を超えると依頼を
  取り消して「止まった」になり、人が上限を上げるか再開すると、同じ段を頼み直します。失敗の数には入れません。
  - p60 で、待ちを時間に数えると、混んだときに1台の ComfyUI を待つだけで作業が止まりました（`V3検証の結果.md` の P60）。
  - 段の活動の打ち切り（start_to_close）は `budget_seconds + wait_seconds` です。待った秒は出来事 `step` の `waited_seconds` に残します。
  - 待ちの数え方は `tests/unit/test_harness_wait_clock.py` で確かめました。本物の混み方で止まらないかは未検証です。
- 送り先への依頼は、今ある順番待ち（GenerationJob）を通します（`queue_calls.py`）。`harness_key` で同じ依頼を重ねません。
  ただし、いちばん新しい依頼が取り消しになっていれば頼み直します。今すぐ止めたあとの再開がこれに当たります。

### 1.1.1 ワークフローの作りを変えるときの決まり
- p60 で、ワークフローの作りを変えた後に、終わった作業を query で読み直すと決定性の誤り（nondeterminism）になりました。
  Temporal は、前の作りで作られた履歴を、今の作りで最初からなぞり直す（replay）からです。
- そこで、**Temporal へ出す命令（活動を始める・待つ時間・子のワークフロー・Signal を送る）の数・順・種類が変わる変更は、
  `workflow.patched("<印の名前>")` の中に書きます。** 新しい道を if の中に、前の道を else に残します。
  - 印の名前は `unit_workflow.py` の先頭に定数で置きます。今ある印は次の3つです（2026-10-08）。
    - `cancel-after-success`：取り消しを頼んだ段が成功で終わっても、頼まれた取り消しを当てる
    - `wait-not-in-budget`：順番待ちを時間の上限に数えず、待ちの上限で持つ
    - `reject-stops`：却下は止まるだけにする
  - 印は消しません。消してよいのは、印より前に始まった作業の履歴が全部消えた後で、そのときは `workflow.deprecate_patch` を挟みます。
  - 命令が変わらない変更（変数の計算・query の返す形・記録の中身）は印が要りません。
  - 活動に渡す dataclass（`StepInput` など）に項目を足すときは、既定の値を付けます（前の履歴の入力が読めるように）。
  - 上限（`limits`）に項目を足したときは、前に始まった作業の `limits` にその項目がありません。印の中で、項目の有無を見てから使います。
- 前の作りの履歴を今の作りでなぞり直す試験（`temporalio.worker.Replayer`）はまだありません。前の作りの履歴を残していないためです
  （未実装）。作るときは、`handle.fetch_history()` で取った履歴を `tests/fixtures/` に置いて、`Replayer.replay_workflow` に渡します。

### 1.1.2 取り消しが消える件（p60）
- p60 で、temporalio 1.34.0 は、取り消しを頼んだ活動が成功で終わると、ワークフローの取り消しを消すと分かりました。
- このサーバーは Temporal のワークフローの取り消しを使わず、取り消しを自前の変数（`cancel_unit_by`・`cancel_step_by`）で持ちます。
  そのため、取り消しそのものは消えません。ただし段の取り消しは、段が成功で終わると黙って捨てられ、作業はそのまま次の段へ
  進んでいました（`test_unit_workflow_timeskip.py` の `段の取り消しは_段が成功で終わっても捨てずに当てる` で再現しました）。
  今は、段が成功で終わっても頼まれた取り消しを当てます（印 `cancel-after-success`）。作業の取り消しは、前から次の段の切れ目で
  止まっていました（同じ試験の作業の取り消しの方は、直す前も通りました）。
- 取り消しの遅れ：p60 は約12秒でした。生存の知らせの間引きが、SDK の既定（生存の知らせの期限の8割）だったためです。
  このサーバーの作業者は、間引きを1秒にしてあります（`harness_worker_main.py`・`queue_worker_main.py` の
  `max_heartbeat_throttle_interval`）。測った遅れは 3 章にあります。

    したときです。上流を見る所（`upstream_watch.py`）は、古い印の出来事を書いてから残りの作業を見て、最後に確定します。その間に

  - 残り（未対応）：snapshot を取った後に確定した、`last_event_id` より小さい id の出来事は流しません。画面がつなぎ直すと snapshot で取り直します。
- ComfyUI の進み具合と途中の絵は `service_call_progress` に書きます（`service_senders/comfyui_progress.py`）。

### 1.3 画面（`v3/web/harness/`）
- 開き方は `/web/harness/?work=<作品の id>` です。共通の帯（`common/nav.js`。`data-v3-nav="harness"`）からも開けます。
- 2つのタブがあります。
  - **工程の図**：S0〜S7 の段と、今の工程の作業を格子に並べます。作業ごとに状態の色と進み具合の帯を出します。
  - **作業の図**：1つの作業の段と、やり直しの線を出します。辿った線には動く印が走ります。生成の段には進み具合の帯と途中の絵を重ねます。
- 図の下には時間の帯があります。右のパネルには次のものを出します。
  - 作業の操作
  - 判断待ちの採用と却下
  - 上限の変更
  - 候補の一覧
  - 工程の検査
- 一番下はページとコマの表です。
- 図は Cytoscape 3.34.3 で描き、並べ方は elkjs 0.11.1（EPL-2.0。`vendor/elkjs-0.11.1/elk.bundled.js`）で決めます。React は使いません。
  ELK は `file://` でも動くように、Web Worker を使わずに同じスレッドで動かします。詳しくは 1.3.1。
- 口は全部 `../js/api.js` の `authFetch` を通します（SSE も）。名乗りの見出し（dev_header のときの `X-V3-User`）と `X-V3-Request: 1` は、ここで1か所で付きます。oidc のときは利用者の欄に名前を出すだけで、書き換えられません。
- **色**：`common/theme.css` の変数だけを使い、色の値は書きません。
  - 状態の色の呼び名（`--run`・`--review` など）は `harness.css` の `:root` の1か所で、theme.css の名前に結ぶだけです。
  - 下地・やり直し・古い・光・斜線（`--run-bg`・`--retry`・`--stale`・`--stale-tint`・`--hot-glow`・`--hot-glow-2`・`--bad-stripe`）は theme.css の決まりの名前です（2026-10-08 に移しました。`V3細部の決めごと.md` 8.1）。
  - 図（`harness_graph.js`）は、この呼び名を `getComputedStyle` で読みます。Cytoscape は CSS の変数も `color-mix()` も読めないので、ブラウザに解かせた色を1画素の canvas で rgb にしています。
  - 色の組を替えるときは `common/themes/` の組のファイルだけを直します。
- **キー・絵だけ・全画面**（2026-10-08）：`startKeys("harness")` を `loadAuth()` のあとで呼びます（`common/keys.js`。`V3細部の決めごと.md` 22章）。絵だけ（Shift+F）は図だけを画面いっぱいに出す見張る画面です（上の帯・画面の帯・右の欄・ページとコマの表に `data-v3-panel`）。図の大きさが変わると `v3-view` を受けて `graph.resized()` を呼びます（1.3.1 の「窓の大きさ」）。0 で図の全体を見ます。試験は `test/keys_ui.mjs`（偽の口）で、写しは `v3/web/screenshots/17_harness_focus.png`。
- **図を開く・たたむ**（拡張は使わず、`harness_graph.js` が要素を足す・消してから並べ直します）
  - 工程の図の作業は「工程の作業 > ページ > 作業」の入れ子のまとまりです。まとまりを押すとたたみ、もう一度押すと開きます。
    帯の「ページごとにたたむ」「全部開く」でも切り替えられます。たたんだまとまりには、作業の数と状態の内訳を出します。
    色は、中で一番急ぐ状態（止まった・判断待ちが先）に合わせます。たたんでいる間に増えた作業は、開いたときに足します。
  - 作業の図では、生成・直させる・検査・評価の段を押すと中を開きます。開ける段のラベルには「＋」、開いた段には「－」が付きます。
    - 生成・直させる：送り先ごとの依頼の数と失敗の数
    - 検査：項目ごとの通る・落ちる・測れないの数
    - 評価：くり返しの回ごとの、比べた数・同点の数・1位
  - 中身は今の回（attempt）の分です。依頼の行は SSE で届かないので、開く・たたむたびに作業の中身を取り直します。
  - 並べ直しは `_relayout()` の1か所だけでします（1.3.1）。
### 1.3.1 図の並べ方（2026-10-08。ELK に替えました）

  | ラベルどうしの重なり | 41 | 0 |

- **作業の図**
  - 横向き（RIGHT）と縦向き（DOWN）の2つを並べ、図の箱の幅に倍率 1 で入る物のうち低い物を取ります。1920×1080 は横向き、
    1280×800 より狭い窓は縦向きになります。縦向きは、ポートの辺を x と y を入れ替えた向きにするだけで、並び順の決まりはそのままです。
  - 縦向きでは辺のラベルを縦書き（1字ずつ改行）にし、横の区間に置くときだけ横書きに戻します。縦の線どうしの間は1字の幅、
    段の間は一番長い縦書きのラベルが入る広さにします（狭いと、隣の段へ入る横の線にかかりました）。開いた段の中の子は
    box で縦に積みます。
  - 段のノードは同じ大きさにそろえます（一番長いラベルが入る大きさ）。開いた段は枠になり、中の子は段ごとに同じ大きさです。
    枠の上の余白は、枠の名前の行の数から決めます。
  - 前へ進む線は右の辺から左の辺へ、戻りの線は上の辺から上の辺へ、飛ばす線（評価なし・判断なし）は下の辺から下の辺へ出します。
    検査→直させるは右の辺から直させるの左へ、直させる→検査は下の辺どうしです。
  - 同じ辺に並ぶポートの順は自分で決めます（`FIXED_ORDER`）。ELK に任せると、戻りの線どうしが入れ子にならずに交わりました。
    左へ行く線を左に、右へ行く線を右に置き、遠くへ行く線ほど外側にします。残る交わりは 3 つで、行き先と出どころの区間が
    互い違いに重なる線どうし（人の判断→生成と検査→文脈など）なので、同じ辺に出す限り消えません。
  - 辺のラベルは ELK に渡しません。ELK はラベルを列の中のノードとして置くので、上・下のポートから縦に入る線と重なりました。
    並べ終えた線の上で、長い区間から、真ん中から左右へずらして、ノード・ほかの線・置いたラベルにかからない所に置きます
    （`placeEdgeLabels`）。並んだ線の間は、ラベルの高さが入る広さにしています（`elk.spacing.edgeEdge`）。
  - 辺のラベルは短くします（却下・作り直す・選べない など）。全文は辺に指を置いたときに図の下の行に出し、通った回数は右の欄の
    「戻った回数」に出します。検査→直させるは置く長さが無く、行き先の名前が中身を言うので、図にはラベルを出しません。
  - 戻りの線は段の列の上、飛ばす線は下を通るので、2つの組は交わりません。それでも交わる所（戻りの線どうしの入れ子が崩れる所）
    には橋を描きます。横の線が縦の線を小さな半円でまたぎます（`findCrossings` と `_drawBridges`。図の上の SVG）。
  - 進み具合は、生成の段の中の細い帯と、図の下の箱（候補ごとの棒・段数・途中の絵）に出します。前は図の上に重ねていて、線と
    ラベルにかかっていました。
- **工程の図**：段の列（layered RIGHT）の下に、工程ごとの作業の枠（box）を置きます。枠の中はページの枠、その中に作業です。
  - 段の列の折り返し（しない・縦横の比 2・1・0.3。ELK の `wrapping.strategy MULTI_EDGE`）、ページの中の作業の詰め方（4通り）、
    工程の作業の枠の中のページの詰め方（3通り）の組 48 通りと、電話の幅のための「段を縦に1列」2通りを全部並べ、
    図の箱の幅に倍率 1 で入る物のうち一番低い物を取ります。30 の作業では 3 列×2 段のページになります。
    1024×768 では段を2つずつ折り返し、390×844 では段を縦に1列に並べます。
  - 作業の枠は、その工程の段の真下に寄せます（`centerGroups`。ELK は下の列を左に詰めるので、枠が段から離れて見えました）。
  - ページと作業の順は、渡された作業の順（`data.ord`）で並べます。box は大きい物から詰めるので、優先度（`elk.priority`）で順を残します。
- **倍率と箱**：全体を見る倍率は 1〜1.25 です。1 より小さくはしません（文字が 12px を割らないように）。図の箱は左の列の残りを
  埋め（`flex:1 0 auto`）、図は箱の真ん中に置きます。縦に入らないときは図の箱を高くします（絵だけの画面のときは高くせず、動かして見ます）。
  どの案も倍率 1 で幅に入らないときは、図の幅を広げて、図の箱の中だけで横に動かして見ます（ページは横に動きません）。
  右の欄の高さが変わって箱の大きさが変わったときは、ResizeObserver で合わせ直します。
- **安定**：並べ直すのは、ノードが増える・消える・大きさが変わるときだけです。状態が変わっただけでは色とラベルを替えるだけで、
  ノードは動きません。
- **並べ直しをまとめる**（2026-10-08）：同じ処理の中で続けて頼まれた並べ直し（読み込みで段と作業を入れる・ページを全部たたむ など）は
  1回にまとめます（`_relayout()` は印を付けるだけで、並べるのは `_layoutLoop()`）。並べている間にまた頼まれたら、その結果は当てずに、
  終わってから今の要素で1回だけ並べ直します。前は頼まれるたびに ELK を回し（工程の図は1回で 50 の案）、最後の1回だけを当てていたので、
  読み込みで 2〜3回、たたむと 3回、案を全部並べていました。今はどちらも1回です。`layoutDone` は、当て終えて頼まれた分が残っていないときに解けます。
- **窓の大きさ**：`resized()` は、今の並びが箱の幅に入るなら倍率だけを合わせます（ノードは動きません）。箱の幅より 8% を超えて
  はみ出すようになったときと、並べたときより 25% 以上広くなったときだけ、並べ方を選び直します。少しだけはみ出すときは並びを変えず、
  箱の中で横に動かします（少し狭めただけで図が組み替わらないように）。
- ELK で分かったこと（elkjs 0.11.1）
  - `elk.json.shapeCoords: ROOT` を付けると、ポートの辺の指定が効かなくなりました。ノードの座標は親からの相対のまま受け、
    足し合わせて図の座標にしています（`_apply` の `walk`）。線は `elk.json.edgeCoords: ROOT` で図の座標で受けます。
  - `crossingMinimization.forceNodeModelOrder` を `cycleBreaking: MODEL_ORDER` と一緒に使っても、ポートの辺が崩れました。使っていません。
  - Cytoscape の `segments` の線に ELK の折れ点を当てるとき、重みと距離の向きが逆になることがあります。4 通りを試して、
    `segmentPoints()` が ELK の折れ点と合う物を使い、合わなければ例外にします（`setEdgeGeometry`）。
- **閾値の欄**：右の欄に、作業が使う閾値の一覧（意味・工程・今の値と状態・案と出典）を出します。案のある所は「案を入れる」、入れた値は「確かめた」で状態を変えます。
- **質問に答える**：企画の聞き取り（S0）の判断待ちでだけ、答えの欄を出します。画像の無い候補（文章の案）も中身を出して採れます。
- **知らせの欄**：未読の知らせ（1.4）と、作品の知らせの決まり（出す種類・Webhook・急ぎに上げる回数・予算の割合）を出します。
  ブラウザの知らせは、人が「ブラウザの知らせを使う」を押して許したときだけ出します（出来事 `notification` を SSE で受けます）。
- **SSE**：`EventSource` は見出しを付けられないので、`authFetch` の stream で読みます（`harness_sse.js`）。
  - 35秒何も来なければ切れたとみなし、「切断中」を出します。
  - つなぎ直すときは snapshot を取り直してから続きを読みます。

### 1.4 知らせ（`harness_notify.py`。決めごと 17章）
- 知らせを作るのは1か所です。ハーネスの出来事を足す所（`harness_record.add_event`）が、出来事ごとに `rules()` を通します。
  どの段・どの口から足した出来事もここを通るので、知らせの漏れが出ません。同じ知らせは `dedupe_key` で1つにします。
- 種類は5つです。
  - 判断待ちになった（`generated`）
  - 止まった・失敗した・決めるまで進めない（`failed`）
  - 予算に近づいた（`budget_near`）：作品の決まりで割合を決めたときだけ出します
  - 判断待ちが長い（`review_overdue`）：`review_notice` を受けたとき。決まりの `escalate_after_notices` 回目から「急ぎ」（`escalated`）に上げます
  - 工程の承認待ち（`stage_review`）
- 出す先
  - アプリの中の一覧：作品の決まりの行が無ければ、全部の種類をここにだけ出します。
  - Webhook：決まりで入れた先にだけ送ります（既定では送りません）。本文に HMAC-SHA256 の署名（`X-V3-Signature`）を付けます。
    「急ぎ」は、送り先ごとの種類の絞り込みに関係なく全部の送り先へ送ります。
    送るのはハーネスの作業者の中の `send_pending_forever` で、失敗したら 5・10・20・40 秒の間を空けて、5回まで送り直します。
  - メール：送る所は作っていません。`CHANNEL_SENDERS` に `email` の送り手を足し、決まりの検査で受ければ、同じ届けた記録と送り直しで動きます。
- 口：`GET notifications`（`unread`・`limit`）、`POST notifications/{id}/read`、`GET`/`PUT notification-settings`。
  署名の鍵は読む口で返しません。保存のとき、同じ URL の鍵を省くと今の鍵を残し、空の文字にすると消します。
- 招いた人の赤入れ・締切（決めごと 19章）の知らせは、ハーネスの出来事に無いので出していません（未実装）。
